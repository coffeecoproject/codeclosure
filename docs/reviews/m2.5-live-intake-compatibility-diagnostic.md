# M2.5 live Intake compatibility diagnostic

- Status: Investigation complete; correction not implemented
- Investigation date: 2026-08-06
- Investigated source: `fb26f34cd2e980c60ed237a3cc1287eb91968b95`
- Historical milestone review: [M2.5 completion review](m2.5-completion-review.md)
- Follow-up plan: [M2.5.1 Real Intake-to-Codex Composition Closure](../plans/m2.5.1-real-intake-codex-composition-closure.md)

## 1. Purpose and evidence strength

This record captures a post-completion compatibility defect discovered by one
real M2.5 Answer-only Intake operation against the already pinned Codex App
Server. It records the bounded investigation result needed to plan a correction.

This record is not M2.5 historical evidence, a replacement milestone verdict,
or proof that the corrected path works. The temporary diagnostic did not retain
an assessment manifest and therefore MUST be reproduced by the M2.5.1 canonical
procedure before any compatibility or composition claim passes.

The investigation did not print or retain user request content, assistant
content, private reasoning, authentication material, account values, raw
notification payloads, or unrestricted exception text. It observed only
protocol method names, closed status values, field names, item types, counts,
and content byte counts. Temporary diagnostic code and temporary operation
state were removed after the investigation.

## 2. Reproduced result

The independent test worktree and the primary repository resolved to the same
source commit. The environment used:

- Node.js `22.22.3`;
- pnpm `11.1.3`;
- Codex CLI `0.146.0`; and
- protocol snapshot
  `sha256:0b0bdf534386d796c41596693c451aabaec2526bbac5a7965ab558edc3de8e21`.

One explicit Answer-only Intake command committed:

- command outcome `APPLIED`;
- Intake outcome `NO_EXECUTION / ANSWER_ONLY`;
- answer disposition `ANSWER_FAILED`;
- failure reason `ASSISTANT_PROTOCOL_ERROR`;
- no Goal;
- no Goal Start Authorization; and
- the expected closed Intake audit chain.

The retained failed Intake Run remains immutable historical authority. A
correction MUST NOT rewrite its outcome. A later proof uses a new command and a
new Intake Run.

## 3. Lower-client comparison

The existing live App Server probe passed authentication, initialization,
Thread creation, Turn completion, structured output, Codex identity, and
protocol-snapshot identity in the same environment.

That result proves the lower client and pinned App Server were reachable. It
does not execute `IntakeProtocolObserver`, does not validate the M2.5 isolated
Intake profile, and does not prove an Intake result. The lower probe therefore
does not contradict the Intake failure and cannot satisfy an M2.5.1 live row.

## 4. Safe protocol localization

The production observer's first rejected event was:

```text
remoteControl/status/changed
status = disabled
```

The event did not enable remote control and was not a Thread Item or external
effect. The observer rejected it because any notification outside its small
benign-method set becomes `ASSISTANT_PROTOCOL_ERROR`.

Temporarily classifying only that exact disabled state for diagnosis exposed
three additional incompatibilities in order:

1. `deprecationNotice` for the explicitly configured deprecated
   `web_search_cached` and `web_search_request` feature keys, even though the
   same closed profile already set top-level `web_search = "disabled"`;
2. `item/started` for an otherwise valid `agentMessage` whose text was empty at
   start and non-empty at completion; and
3. `account/rateLimits/updated`, a process/account projection rather than an
   Intake Item, tool call, or authority effect.

After diagnostic-only bounded handling of those events, the operation reached a
valid terminal shape:

- the exact bound Thread and Turn;
- `status = completed`;
- `error = null`;
- `itemsView = summary`;
- exactly one final `agentMessage`;
- one exact completed-message-to-terminal-summary digest match; and
- one response object with the closed `answerContent` string field.

The diagnostic `selectFinalText` path succeeded. Terminal-summary binding and
the Answer-only response structure were therefore not the observed cause.

## 5. Root cause and contract classification

The defect is in the M2.5 Intake Adapter implementation and closed profile, not
in authentication, the pinned version, terminal summary, response schema, or
accepted model behavior.

The implementation is too strict in two ways:

- it interprets every unlisted pinned notification as forbidden activity,
  rather than distinguishing operation lifecycle, harmless process projection,
  and authority-bearing or effect-bearing activity; and
- it applies the completed-message non-empty-text invariant to
  `item/started`, where progressive message text may still be empty.

The controlled configuration additionally requests deprecated keys and then
treats the resulting compatibility notice as an unexpected protocol event.

The structural correction is not to keep expanding the Observer's benign
method set. The current Observer is coupled directly to raw Codex notification
methods, so upstream lifecycle detail and Intake lifecycle authority are mixed
in one switch. M2.5.1 instead introduces one Adapter-local typed protocol
projection and exhaustive effect classifier. The Observer will receive only a
small closed normalized event union and will remain responsible for correlation,
order, terminal binding, and response handoff rather than upstream method
compatibility.

[ADR 0035](../adr/0035-bound-intake-by-non-authoritative-effects.md) requires
failure after an observed command, file change, image, MCP, dynamic-tool,
approval, or other effect-bearing Item. A compaction observation remains a
separate fail-closed protocol violation. The ADR does not require rejection of
a valid disabled remote-control projection, rate-limit projection, or
progressive message-start lifecycle. Correcting those classifications conforms
the Adapter to the accepted boundary; it does not weaken failure closure.

## 6. Historical proof boundary

The [M2.5 completion review](m2.5-completion-review.md) explicitly records that
no optional live M2.5 Intake Assistant observation satisfied an M2.5 row. Its
Adapter proof used controlled fixtures, and its governed-execution proof bound
the M1 happy-path FakeWorker Execution Profile.

The historical `PASS` remains valid only for that recorded bounded claim and
source identity. This defect record MUST NOT be used to state that M2.5 had
already proven:

- a successful real Intake Assistant operation;
- M2.5 Materialization selecting the real M2 Codex Execution Profile;
- ordinary Start dispatching from M2.5 into the real Codex Worker; or
- a complete real Intake-to-Candidate-to-Acceptance product path.

The existing M2 protected demonstration is not an all-real phase composition
that can simply be extracted into M2.5.1. Its external Codex Profile selects
only `IMPLEMENT`, and its candidate-free `DISCOVERY`/`PLAN` Worker dependency
is `FakeWorker`. The accepted Domain permits an external Profile to select
those candidate-free phases, but the current trusted Codex invocation rejects
non-`IMPLEMENT` requests and has no completed bounded project-read composition
for them. This is a current composition fact, not a defect in the historical M2
verdict.

## 7. Required correction boundary

The compatibility correction must:

- retain the lower App Server Client as the raw JSON-RPC frame decoder and
  introduce one Adapter-local typed `IntakeProtocolProjection` as the sole
  successfully decoded notification consumer above that boundary;
- exhaustively validate the pinned notification method union and map a closed,
  minimized protocol fact through a private `IntakeEffectClassifier` into a
  small closed `IntakeObservedEvent` union;
- make `IntakeProtocolObserver` consume only normalized lifecycle, benign
  process-projection, forbidden-effect, and protocol-violation events rather
  than raw Codex methods;
- remove the Intake `onCompactionEvent` side channel so compaction cannot bypass
  the Projection;
- accept remote-control status only under the exact disabled shape already
  permitted by the M2 Worker boundary;
- validate and discard rate-limit projection content without retaining account
  values;
- distinguish started and completed agent-message invariants;
- remove the two deprecated Web Search feature keys while retaining the exact
  top-level disabled state;
- keep unsupported methods and malformed envelopes fail-closed in the lower
  Client; map `thread/compacted`, a `contextCompaction` Item, known-method
  malformed params, warning, reroute, and other unclassified lifecycle
  activity to one `PROTOCOL_VIOLATION` disposition; map tool, command,
  file-change, image, MCP, dynamic-tool, approval, and other effect-bearing
  activity to `FORBIDDEN_EFFECT_OBSERVED`; both classes fail the operation;
- retain only closed diagnostic categories, never notification payloads or raw
  exception text; and
- introduce new profile/adapter identities for changed closed configuration and
  behavior without reinterpreting historical version-1 records.

The normalized events remain internal to the Adapter and add no Domain,
Runtime, Store, Audit, Admission, Goal, Start, Evidence, or Acceptance record.
Unsupported or malformed lower-client input closes the Client, while malformed
or unmapped successfully decoded activity becomes a protocol violation. Neither
path becomes benign by default.

The broader real composition closure must separately prove that trusted Runtime
composition, not user or model output, selects the exact real M2 Codex
Execution Profile bound by `GoalStartAuthorization` and later resolved by the
ordinary Start path. Its formal phase mapping must use real candidate-free
Codex execution over exact Runtime-owned read-only selected-source snapshots
for `DISCOVERY`/`PLAN`, real Candidate-bound Codex execution for `IMPLEMENT`,
and no production FakeWorker fallback. The checkout itself remains unreadable;
project configuration and instruction sources cannot widen the bound phase
Profile. Slice 0 must close and accept
[ADR 0043](../adr/0043-candidate-free-codex-project-read-authority.md), or an
exact replacement decision, because ADR 0015 keeps project-source Context
closed until a later accepted ADR supplies that authority.

## 8. Milestone disposition

The Adapter protocol-projection and closed-profile change is an M2.5
compatibility correction. The real Intake-to-M2 Worker product composition and
mandatory live evidence are the separate proposed M2.5.1 closure. M2.5.1 is an
entry condition for M2.6 implementation and assessment; it is not an M2.6
Frontstage feature.

No M2.6 implementation scope should expand until the M2.5.1 canonical
assessment and independent review have passed on one exact source identity.
