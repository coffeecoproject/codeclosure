# M2.5.1 Slice 2 Real Intake Compatibility Review

- Review date: 2026-08-08
- Scope: M2.5.1 Slice 2 only
- Status: Implemented and validated against the pinned real Codex App Server
- Verdict: `PASS`; Slice 3 may begin, but no real Goal-bound phase
  composition, M2.5.1 milestone completion, or M2.6 work is claimed

## Review question

This review asks whether the corrected M2.5.1 Intake path works through real
Codex `0.146.1` for Answer-only, clear Intent, and ambiguous Intent while
preserving Runtime-owned provenance and deterministic Admission authority.

It does not ask whether Materialization and ordinary Start reach the real M2
Codex Execution Profile. Candidate-free `DISCOVERY`/`PLAN`, Candidate-bound
`IMPLEMENT`, protected verification, Evidence, Acceptance, and closeout remain
Slice 3 and later work.

## Root-cause findings

The lower-client live prerequisite continued to pass initialization, one
structured-output Turn, shutdown, and controlled-state cleanup. Temporary
content-free diagnostics then localized the original Intake failure without
retaining request, answer, reasoning, account, authentication, notification,
or exception content.

The real incompatibility was a combination of four version-bound assumptions:

1. the effective `config/read`, permission-profile, Thread, service-tier, and
   benign notification projections were narrower than the valid pinned
   `0.146.1` surface;
2. the historical Intent schema omitted optional properties from `required`
   and used `uniqueItems`, which is outside the pinned strict structured-output
   subset used by the live service;
3. the model-authored byte-coordinate suggestions were probabilistic and could
   be missing or invalid even after a valid Intent Turn; and
4. the new live receipt initially treated the Domain's explicit
   `NOT_REQUESTED` answer disposition as `null` for non-Answer operations.

The fourth item was only a new assessment assertion defect. The first three
required versioned product-contract corrections; none justified weakening
failure closure or reinterpreting historical M2.5 authority.

## Implemented boundary

New M2.5.1 operations use a new Assistant Profile/Adapter identity set because
the closed configuration, projection rules, instruction policy, response
schema, and Runtime projection behavior changed:

- Assistant Profile `codeclosure-m2-5-1-local-assistant-v3`, schema 3;
- Assistant Adapter `codeclosure-m2-5-1-intake-adapter-v3`;
- closed configuration `codeclosure-m2-5-1-local-config-v2`; and
- protocol projection policy `codeclosure-m2-5-1-projection-v2`;

- Intent response contract
  `codeclosure-m2-5-1-intent-analysis-response-v2`;
- exact-source instruction policy
  `codeclosure-m2-5-1-exact-source-instructions-v1`; and
- Runtime Intent projection profile
  `codeclosure-m2-5-1-exact-value-match-v3`.

The strict v2 wire schema requires every property, represents optional values
as nullable, removes the unsupported uniqueness keyword, and requires
`candidateSourceSpanSuggestions` to be empty. Adapter-local decoding converts
nullable wire values into the existing optional non-authoritative response
shape and still enforces byte budgets, unique strings, exact keys, and all
other local semantic constraints.

The versioned instruction policy requires explicitly labelled Objective,
Required criterion, and Scope values to be copied exactly rather than
paraphrased. Runtime independently searches only the Manifest-selected retained
user bytes for byte-identical proposed values and constructs `USER_STATED`
bindings itself. A missing or paraphrased value remains `MODEL_PROPOSED` and
cannot satisfy Admission. The assistant does not choose a Source Binding,
authority class, ambiguity, Decision, Goal, or Start result.

Historical M2.5 v1 packages keep their original response schema, assistant
span-suggestion behavior, and `codeclosure-m2-5-projection-v2` projection
profile. Strict reopen, replay, and failure reconciliation do not upgrade or
rehash them.

Slice 1's v2 Profile/Adapter, configuration v1, and protocol projection v1 are
also retained with their original meaning. They can be strictly decoded and
reconciled, but are never silently recalled through Slice 2 behavior; direct
v2 invocation closes before process launch. New operations compile only v3.

The effective configuration v2 and protocol projection v2 were aligned to
the observed pinned surface. The Adapter validates and discards permitted
runtime extension fields and benign projections, rejects unknown or enabled
capabilities, retains only fixed content-free error classes, and exposes only
bounded Adapter-authored diagnostic tokens.

## Live evidence

The explicitly authorized command was:

```text
CODECLOSURE_M251_LIVE_AUTHORIZED=1 corepack pnpm probe:m2.5.1:intake:live
```

The command first ran the separate lower-client prerequisite and then launched
three isolated Intake processes. Its validated metadata-only receipt recorded:

| Path | Runtime-owned result |
| --- | --- |
| Answer-only | `NO_EXECUTION / ANSWER_RETURNED`; no Proposal, Goal, or Start authority |
| Clear Intent | one Proposal, Projection, Decision, and Question; three `USER_STATED` bindings for Objective, Required criterion, and Scope; the existing M2.5 scope rule selected the exact Scope Question; no Goal or Start authority |
| Ambiguous Intent | one Proposal, Projection, Decision, and Required criterion Question; Objective and Scope remained exact `USER_STATED`; no Goal or Start authority |

Each path recorded exactly one fresh process, Thread, and Turn, with no
interrupt, Compact, retry, forbidden effect, project observation, project
change, Goal, or Start authorization. All Thread and Turn references were
unique. Per-scenario operation roots, temporary state, and the aggregate
assessment root were removed. The receipt contained no request or assistant
content, reasoning, transcript, raw payload, exception, credential, account,
or rate-limit value.

Before the lower prerequisite, and again after every scenario and assessment
root was removed, the command captured the canonical full-content source
manifest while excluding only this self-referential review. Opening and closing
identities had to match exactly; a Git revision plus path/status digest was not
treated as sufficient source identity. For each project-bearing scenario, the
receipt also compared a deterministic manifest of the complete temporary
project tree, including its root, directories, regular files, symbolic-link
targets, permission modes, and file-content digests. Added, removed, renamed,
retargeted, mode-changed, or content-changed entries therefore close the live
proof instead of being hidden by an unchanged sentinel file.

The matching opening and closing source identity contained 1,023 paths and
manifest digest
`sha256:38514458f5b88c29c714f8c03176e700b5f745984466009ac4dba286ecac6ab4`.
Both project-bearing scenarios contained two project-tree entries and matching
opening/closing digest
`sha256:8c8fbdec2a42b78dc743ae7fb46df2042684d98c2e9f29df3a7f726dadd225d2`.

The clear path intentionally did not claim Materialization: the accepted M2.5
policy treats the explicit Scope value as material clarification. Slice 2 proves
real Intent analysis and Runtime-owned binding/Admission input, while the
qualified clarification-to-Materialization path remains a later mandatory row.

## Verdict

`PASS` applies only to M2.5.1 Slice 2 real Intake compatibility. The exact
versioned Adapter, response, instruction, and Runtime projection chain now has
mandatory real Answer-only and Intent-analysis evidence. Slice 3 may begin the
separate trusted M2 Execution Profile composition. M2.5.1 remains incomplete,
and M2.6 must not begin.
