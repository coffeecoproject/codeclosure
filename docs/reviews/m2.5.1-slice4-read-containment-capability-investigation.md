## 1. Purpose and evidence strength

This record closes the bounded capability investigation required after the
pinned Codex `0.146.1` candidate-free `readOnly` command opened a content-free
Authority Home sentinel. It distinguishes backend incapability from an
incorrect CodeClosure composition of an otherwise supported permission
surface.

This record is non-authoritative engineering evidence. It does not install or
change an Execution Profile, change retained authority, authorize a production
Worker operation, unblock B5, or issue a Slice 4 or milestone verdict. The
formal production mapping now exists, but its complete real Worker proof
remains pending.

## 4. Contract interpretation

Both versions generate the same `SandboxPolicy.ts` bytes with digest
`sha256:f5a4b24c0de4945e77c1573306ae4cb98a29103a6c64ee23264dc9d35a977e85`.
That request-level union contains only `dangerFullAccess`, `readOnly`,
`externalSandbox`, and `workspaceWrite`; it does not contain the current
manual's nested restricted-read members.

That fact does not exhaust the stable permission surface. Both versions also
support:

- controlled `default_permissions` configuration;
- custom permission profiles with root denial, minimal toolchain reads,
  per-workspace `read` or `write`, explicit `.git` and local-control denial,
  and disabled network;
- exact `permissionProfile/list` observation;
- optional Thread sandbox selection, which permits the configured default to
  remain effective when no request override is supplied; and
- optional `command/exec.sandboxPolicy`, whose omission applies the configured
  default permission policy.

The failed B4 command supplied a generic request-level `readOnly` policy. That
policy prevented writes but replaced the custom readable-root perimeter. The
absence of a new restricted member in `SandboxPolicy.ts` therefore did not
prove backend incapability.

## 5. C2 method and privacy boundary

The investigation used isolated temporary roots and official exact binaries.
It copied the existing lower Client into the temporary root and added one
diagnostic-only `DEFAULT_PROFILE` branch to its already bounded
`command/exec` method. That branch preserved fixed argv, absolute cwd, output
cap, timeout, response decoding, initialization, process ownership, and clean
shutdown; it only omitted the request-level `sandboxPolicy`. It did not expose
a generic method, arbitrary configuration, or product API, and the entire copy
was removed afterward.

For the selected retained baseline, separate candidate-free and Candidate-
bound App Server processes used one exact custom default profile each:

- candidate-free workspace access `read`;
- Candidate workspace access `write`;
- root default `deny` plus minimal toolchain `read`;
- temporary-root denial and network disabled; and
- no request-level Thread or command sandbox override.

The matrix used only empty sentinels and shell file-descriptor opens or empty
file creation with stdout and stderr suppressed. It retained no path-bearing
command output, protected content, source bytes, request text, assistant
content, reasoning, credentials, account values, raw protocol, or raw
exception. It made no model call and started no Turn. All owned App Server
processes closed and all temporary package, Client, state, and matrix roots
were removed.

## 7. Root cause and ownership

The root cause is a CodeClosure composition defect across already correct
owners:

1. Profile v3 phase entries already own exact phase-local
   `permissionProfileId` and digest, but production preparation currently fills
   every phase with one shared permission profile.
2. That shared profile grants workspace `write`, even for `DISCOVERY` and
   `PLAN`.
3. The Worker Adapter supplies generic sandbox overrides at Thread and Turn
   creation instead of inheriting the exact phase-selected default profile.
4. The B4 lower Client similarly always emits request-level `readOnly` or
   `workspaceWrite`, so its direct probe does not exercise the same permission
   authority as the formal phase.
5. Effective-isolation checks encode those generic projections and therefore
   validate the substituted policy rather than the phase profile.

The owning correction remains below Runtime workflow authority: trusted
profile preparation must bind a read-only ProjectRead profile and a writable
Candidate profile; controlled launch must select the exact phase profile;
Adapter Thread/Turn requests and the direct probe must inherit that selection;
and effective checks must bind the resulting exact profile and projection.

This does not require Domain, Store, Workflow, Candidate, Evidence, or
Acceptance schema changes. The existing Profile v3 phase entry is already the
single authority for the required identity.

## 8. Closed conclusion and next boundary

The exact C3 conclusion is:

```text
SUPPORTED_CODEX_READ_CONTAINMENT_PROVEN
```

The selected implementation route retains Codex `0.146.1`. It is a focused
correction under accepted ADR 0028's custom least-privilege permission profile
and ADR 0043's phase-bound ProjectRead/Candidate containment contract. It does
not change a durable architecture decision, so no new ADR is required.

Before B5 can restart, production code MUST:

- preserve the reviewed Profile v1 tuple and select one additive Profile
  version/digest for new operations rather than silently changing retained
  authority;
- materialize exact read-only and writable permission profiles in one
  controlled configuration;
- select the phase entry's exact profile through a narrow controlled-launch
  field rather than a caller-authored arbitrary config string;
- add a narrow lower-client command method that inherits only that selected
  configured profile while retaining all existing command bounds;
- remove Thread and Turn sandbox overrides from the v3 Worker path and verify
  the inherited effective isolation;
- preserve historical M2 and pre-v3 Adapter behavior unchanged;
- add substitution, omitted-selection, explicit-override, forbidden-root,
  cleanup, and failure-closure tests; and
- pass the formal deterministic suites and the existing complete Live B4
  matrix on one exact supported production identity.

The production code and deterministic requirements in this list are now
implemented. The last Live-matrix requirement remains pending and is the reason
B5 is still blocked.

Only then may B5 restart from the beginning. This capability investigation is
not itself formal real Worker, linked user-path, Slice 4, or milestone evidence,
and it does not alter any historical M1, M2, M2.5, or Slice 0 through Slice 3
verdict.
