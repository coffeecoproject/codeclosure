## Needs M2.6 decision before implementation

### Direct-action and confirmation vocabulary

Define the exact closed direct-action grammar, directly authorizable action
kinds, natural-language confirmation/decline phrases, locale, and normalization
rules for the bounded proof. Neither parser may become an unrestricted model
classifier. The formal decision belongs in ADR 0036 or its replacement.

### Immutable action dispatch and crash reconciliation

Close the exact `PendingAction` -> `PendingActionResolution` ->
`InteractionActionReservation` -> `InteractionActionOutcome` relationship,
including preallocated public Command ID, canonical input, unique consumption,
and failure windows before/after public command commit. Assistant operations
terminalize without model recall; an already authorized public action may use
only same-Command-ID idempotent replay. The decision belongs in ADR 0036 and
ADR 0039 plus the acceptance matrix.

### Busy-session action disposition

Close the exact result when one session-owned execution-bearing task is active
and the user requests another governed Intake, Start, Resume, Cancel, or
`MATERIALIZE_ONLY` Intake. M2.6 must allow read interaction and confirmed
cancellation, must not launch or retain a second execution task, and may offer
`MATERIALIZE_ONLY` only as an exact separately authorized alternative. This is
local composition, not a project slot. The decision belongs in ADR 0036 and
ADR 0039.

### Trusted parser and Assistant operation sequence

Freeze confirmation/decline, focused Intake Question, direct-action, and
read-query parser ordering. Close the single `FrontstageProposalResponse`
union and prove that one user message invokes at most one Assistant operation.
The decision belongs in ADR 0037 and the response-contract acceptance rows.

### Session selection on startup

Choose whether trusted startup always creates a new session or may resume the
sole open session for the same principal/project. Ambiguous selection must fail
closed. The decision belongs in ADR 0039 and the acceptance matrix.

### Goal summary filters and page limits

Close exact filter enum, ordering key, default active subset, page size, cursor
identity, objective truncation, retention/redaction rules, and the binding of
the fixed local principal to one verified authority home plus exact normalized
project path. Do not add per-Goal principal authority in M2.6. The decision
belongs in ADR 0038 and the public query contract.

### Graceful interruption deadline

Close the bounded shutdown deadline and exact result when the active Goal task
does not reach a persisted interruption point before process exit. This must
reuse existing Runtime recovery rather than invent CLI-owned Workflow state.

### App Server compatibility identity

Record the exact installed version/profile used by the M2.6 proof after a
bounded read-only capability probe. Do not copy M2.5 identities without
verification and do not claim an empty built-in tool inventory.

### README status-source contract migration

The executable documentation check still requires the root `Status` section to
link the historical M2 plan plus milestones. Decide and review whether M2.6
formalization should migrate that sole detailed-plan target to the M2.6 plan,
then update `AGENTS.md`, the checker, and its tests in one change. Until then,
do not add a competing M2.6 link inside the root `Status` section.

## Assign to M3 — Fact Graph and Context

### Project-aware ordinary conversation

If ordinary answers may inspect a repository, define a narrow project-read
port, exact project/source identity, path/symlink rules, budgets, provenance,
retention, audit, omissions, and stale-observation behavior. Ambient assistant
tools are not a substitute.

### Composite multi-message user provenance

If several natural-language messages should jointly support `USER_STATED`
Goal fields, define an explicit composite-source record and compatible
RawRequest/Source Binding/Admission changes. Runtime-authored concatenation or
model summary cannot be retrofitted into M2.5 authority.

### Long-term session facts and relevance selection

Durable conversational facts, business-scenario relationships, relevance
selection, omission policy, and context budgets belong with the Fact Graph and
Context Compiler. A transcript remains non-authoritative until such records
are admitted through their owning policy.

### Goal revision from conversation

Changing an already materialized Goal from later conversation requires a
source-bound Goal Revision Proposal and a separate
`GoalRevisionAdmissionDecision`. M2.6 uses cancel/new Intake for semantic
correction and does not silently revise Goal intent.

### Persistent assistant Thread and Compact policy

Evaluate Thread reuse only after authoritative context selection and omission
records exist. Retaining or compacting a Thread must not change Goal, Intake,
Focus, pending action, Evidence, or Acceptance authority.

## Assign to M4 — recovery and operator UX

### Rich Human Decision and notification UX

Full blocker/decision prompts, durable notification delivery, notification
acknowledgement, offline queues, desktop integration, and richer status views
belong with the Human Decision Gateway/operator milestone. Notifications
remain derived projections and never become completion authority.

### Long-term privacy, deletion, and retention controls

M2.6 needs one bounded retention profile. Search, export, deletion/erasure,
long-term sensitive-message policy, and model-provider data controls require a
broader privacy design with explicit authority-preserving tombstone behavior.

### Automatic retry and repair continuation

Conversation must not imply another repair attempt. Maximum rounds, budgets,
backoff, no-progress detection, change-strategy/request-user/stop outcomes, and
recovery belong to M4's explicit continuation authority.

## Assign to M5 — scheduling and broader deployment

### Automatic multi-Goal scheduling

Priority, dependency, fairness, pause/preemption, resource budget, queue
recovery, and user override policy belong to an explicit scheduler. The
frontstage may list Goals but must not choose and launch the next Goal
automatically in M2.6.

### Parallel workers and multi-agent coordination

Parallel Goal workers, model voting, independent Reviewer workers, and agent
handoff need explicit authority, Candidate, Evidence, cost, and failure
semantics. They are not a frontstage feature.

### Multi-user, team, remote, and cloud operation

Authentication, authorization, tenant/project isolation, remote workers,
network trust, distributed locks, audit export, and shared Goal control remain
outside the local single-principal M2.6 claim.

### Promotion and release actions

Merge, release, deployment, communication, purchase, and production mutation
require a separate post-closeout gateway. Natural-language confirmation of an
M2.6 pending action cannot authorize them.

## Rejected for the current direction unless a new decision reopens them

- menu-first or slash-command-first interaction as the primary M2.6 user path;
- model-authored trusted route/action records;
- raw Store access from the frontstage or assistant;
- interpreting `turn/completed`, answer text, notification, or status rendering
  as Goal completion;
- automatic CLI-exit cancellation;
- unrestricted assistant tools; and
- a silent compatibility layer for IntentOS commands, schemas, or manifests.
