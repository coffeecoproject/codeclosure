## 1. Purpose

This document defines the planned independent executable exit assessment for
the bounded M2.6 milestone. It must eventually convert every mandatory claim
below into exact test ownership, raw evidence, and a zero-skip verdict matrix
over one source identity.

This plan is not implementation evidence and issues no Route Decision, pending
action, Goal/Workflow mutation, technical Acceptance, milestone verdict, or
external-effect authority.

## 3. Acceptance question and bounded claim

The independent reviewer answers exactly:

> Does the exact reviewed source provide one continuously available local CLI
> frontstage where a user can use natural language for bounded conversation,
> M2.5 Intake, scoped Goal discovery/status/control, and one in-process Goal
> execution while CodeClosure retains exact routing, pending-action,
> immutable authorization/action-dispatch, direct-or-separate confirmation,
> replay, recovery, Workflow, and Acceptance authority?

An unconditional `PASS` proves only that claim. It does not prove:

- detached execution after CLI exit;
- automatic multi-Goal scheduling or a project-wide execution slot;
- rich TUI, multi-user, remote, or cloud behavior;
- full Fact Graph or project-aware ordinary chat;
- long-lived model memory or Thread continuity;
- automatic repair/retry or Goal revision;
- arbitrary-project verification completeness; or
- merge, release, deployment, promotion, or product completion.

## 4. Entry conditions

The assessment MUST NOT start until:

1. M2.5 remains independently accepted for its exact historical bounded claim;
2. M2.5.1 has passed every mandatory deterministic and live row plus an
   independent completion review, proving the current real Intake-to-M2 Codex
   composition without retroactively changing M2.5 evidence;
3. every M2.6 Slice 0 through 7 deliverable is implemented with focused review
   evidence, without a milestone verdict;
4. ADR 0036 through ADR 0039 remain accepted and no proposed ADR is treated as
   binding;
5. the working tree and exact source identity are recorded before execution;
6. Node, pnpm, manifest, lockfile, and SQLite migration range are compatible;
7. fixed routing, direct-action, confirmation, assistant, response, retention,
   budget, Workflow Policy, and Execution Profile identities are recorded;
8. deterministic assistant and Worker fixtures plus failure-injection seams are
   available through public test composition;
9. a canonical `accept:m2.6` command names every mandatory stage and declares
   only the later completion-review path as its source exclusion;
10. no M2.7, M3, M4, or M5 capability is required by the fixed M2.6 claim; and
11. no higher-authority conflict or unreviewed scope change remains.

Failure to establish an entry condition yields `BLOCKED`, not partial pass.

## 5. Required evidence contract

The canonical runner must produce:

- source-manifest schema/version, base revision, branch, opening/closing status,
  ordered path digests, aggregate digest, and sole review exclusion;
- environment/toolchain/App Server/SQLite identities;
- exact installed policy/profile/response/budget identities;
- raw stdout/stderr, exit status, duration, and digest for every stage;
- one receipt for every mandatory matrix row naming its exact test and raw
  artifact;
- pass/fail/cancel/skip/todo counts parsed from each invoked runner;
- strict-reopen applicability and result for every authority-bearing row; and
- final machine-readable `READY_FOR_INDEPENDENT_REVIEW` or fail-closed
  readiness result.

The canonical runner does not issue or persist the milestone verdict. Any
failed, cancelled, skipped, todo, missing, waived, unexpected “not applicable”,
source-drift, or evidence-integrity row prevents readiness.

## 8. Required demonstrations

The canonical deterministic demonstration follows the ten-step path in the
[implementation plan](m2.6-unified-frontstage-interaction.md#7-required-walking-demonstration).
Its raw evidence must show exact Interaction, Intake, Goal, Workflow, command,
audit, and reopen identities rather than relying on rendered prose.

The authorized live proof is intentionally narrower. It must establish that
the supported installed App Server can complete one isolated route or ordinary
answer operation under the fixed Frontstage profile, and that a subsequent
deterministically directly authorized governed request enters the already
accepted M2.5/public Runtime path without model-authored authorization. Live
model quality does not decide the milestone; deterministic fixtures own route,
confirmation, failure, replay, and authority adversaries.

## 9. Independent review procedure

The independent reviewer must:

1. verify source and evidence-manifest integrity;
2. read the complete authority set and inspect actual source/diff/migrations;
3. confirm every matrix receipt against raw output and exact named tests;
4. inspect static package boundaries and trusted composition, not only runtime
   behavior;
5. inspect SQLite schema/triggers/reopen validation and failure injection;
6. compare the claimed non-scope with the implementation and owning milestone
   assignments;
7. rerun the review-bearing offline gate after adding only the excluded review
   file; and
8. issue exactly one unconditional `PASS`, `FAIL`, or `BLOCKED` for the bounded
   acceptance question.

The review must explicitly distinguish:

- formal documentation ready;
- implementation slices complete;
- executable assessment ready;
- bounded M2.6 milestone complete; and
- CodeClosure product complete.

Only the fourth is the possible `PASS` claim here. The fifth is not established
by M2.6.
