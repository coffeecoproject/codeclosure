## 1. Purpose

This document defines the proposed independent executable exit assessment for
the bounded M2.7 Runtime Host, project control lease, read-only secondary CLI,
and one-active-Goal project slot.

It is not implementation evidence and cannot issue Host ownership, a control
lease, Goal execution, technical Acceptance, milestone verdict, or external-
effect authority.

## 3. Acceptance question and bounded claim

The independent reviewer answers exactly:

> Does the exact reviewed source run one compatible local Runtime Host that
> continues existing governed Goal execution across CLI detach/reconnect,
> permits one writable controller plus bounded observers per principal/project,
> and atomically limits each project to one started non-terminal Goal without
> adding a queue, automatic handoff, or new completion authority?

An unconditional `PASS` proves only that claim. It does not prove:

- automatic Goal ordering, queueing, priority, or next-Goal Start;
- multiple active Goals or parallel workers in one project;
- multi-user/team, remote, distributed, or cloud hosting;
- indefinite service availability or zero-downtime Host upgrades;
- full Fact Graph, Goal Revision, automatic repair, or rich operator UX;
- arbitrary-project verification completeness; or
- promotion, release, deployment, external effects, or product completion.

## 4. Entry conditions

The assessment MUST NOT start until:

1. M2.6 has an independent bounded `PASS`;
2. all M2.7 implementation slices through Slice 7 are complete with focused
   evidence and no milestone verdict;
3. ADR 0040 through ADR 0042 are accepted or replaced;
4. source identity, branch/base, working-tree state, toolchain, migration range,
   Host executable/configuration, transport, lease, and slot policy identities
   are recorded;
5. deterministic Host/client/Worker/process fixtures and failure injection are
   available through trusted proof composition;
6. fresh and retained Store migration cases are fixed, including ambiguous
   historical active Goals;
7. canonical `accept:m2.7` names every mandatory stage and only the later
   completion-review path as source exclusion;
8. no scheduler, delayed automatic-Start, or multi-user feature is hidden in
   the implementation; and
9. no higher-authority conflict remains.

Failure to establish an entry condition is `BLOCKED`, not a partial pass.

## 5. Required evidence contract

The canonical runner must retain:

- opening/closing source manifests, base revision, ordered path digests,
  aggregate digest, and sole review exclusion;
- environment, OS/process, Node/pnpm/SQLite/App Server, Host executable,
  transport, endpoint, policy/profile, and schema identities;
- raw output, exit status, duration, and digest for every stage;
- one exact receipt for every matrix row and named test;
- pass/fail/cancel/skip/todo counts for every invoked runner;
- strict-reopen applicability/results for every authority-bearing row;
- bounded live authorization separately from deterministic evidence; and
- machine-readable readiness that cannot issue the milestone verdict.

Any failed, cancelled, skipped, todo, missing, waived, source-drift, evidence-
integrity, or unexpected-not-applicable row prevents readiness.

## 8. Required demonstrations

The deterministic demonstration follows the ten steps in the
[implementation plan](m2.7-local-runtime-host-single-goal-control.md#7-required-walking-demonstration).
Raw evidence must bind Host/Control Epochs, lease, slot, commands, Goal/Workflow,
external execution, audit, and reopen state rather than relying on rendered
messages.

The authorized live proof is narrow: one supported Host remains active after
the CLI detaches while one existing bounded live Codex Goal path proceeds; a
later CLI reconnects and reads the exact Runtime-owned result. Model quality
does not decide Host, lease, slot, race, migration, or recovery rows.

## 9. Independent review

The reviewer must validate source/evidence identity, inspect all authority
documents and actual code/diff/migrations, verify every row against raw output,
inspect static package/transport boundaries, inspect Store schema/triggers/
reopen/failure injection, confirm non-scope contains no hidden queue, and rerun
the review-bearing offline gate after adding only the excluded review file.

The final review issues exactly one unconditional `PASS`, `FAIL`, or `BLOCKED`
for the bounded question and explicitly distinguishes documentation,
implementation, assessment readiness, M2.7 completion, and product completion.
