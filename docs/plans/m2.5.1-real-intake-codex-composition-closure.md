## 1. Purpose and completion meaning

M2.5.1 closes two post-M2.5 product-composition gaps before M2.6 begins:

1. make the pinned real Codex App Server compatible with the already accepted
   bounded Intake authority/effect contract; and
2. compose M2.5 Goal Materialization and ordinary Start with one trusted real
   Codex phase mapping: candidate-free Codex execution over exact Runtime-owned
   read-only selected-source snapshots for `DISCOVERY` and `PLAN`, followed by
   candidate-bound Codex execution for `IMPLEMENT`, instead of the M1
   FakeWorker profile used by the historical M2.5 proof.

The milestone proves one bounded real local path from explicit Intake action to
real Codex Worker execution in an isolated Candidate. It does not add natural-
language frontstage routing, a Runtime Host, scheduling, arbitrary-project
verification completeness, automatic repair, release, or deployment.

Completing this plan creates only an implementation candidate. M2.5.1 becomes
complete only after its canonical mandatory-live assessment and an independent
dated review issue an unconditional bounded verdict.

## 7. Intake protocol projection and effect classification

M2.5.1 must not grow a notification whitelist inside
`IntakeProtocolObserver`. The Adapter instead owns one explicit typed
translation boundary:

```text
raw JSON-RPC frame
  -> Codex App Server Client
       |-- unsupported/malformed envelope -> closed client protocol failure
       `-- successfully decoded AppServerNotification
             -> IntakeProtocolProjection
                  |-- known-method malformed params -> PROTOCOL_VIOLATION
                  `-- validated minimal protocol fact
                        -> private IntakeEffectClassifier
                        -> closed IntakeObservedEvent
                             -> IntakeProtocolObserver
```

The lower Client remains the sole raw JSON-RPC frame decoder and owns generated
notification-method admission, envelope shape, protocol limits, correlation,
and its internal compaction tracking. An unsupported method or malformed
envelope closes the Client and maps through the Adapter to
`ASSISTANT_PROTOCOL_ERROR`; it does not become a fabricated normalized event.

Above that lower boundary, `IntakeProtocolProjection` is the only Intake Adapter
component that may receive a successfully decoded `AppServerNotification`. It
is the sole `onNotification` target, exhaustively switches over the pinned
method union, performs method-specific exact runtime validation because the
lower envelope still carries generic JSON params, and emits exactly one
Adapter-local `IntakeObservedEvent` variant. Intake composition must not wire
the lower Client's `onCompactionEvent` callback to the Observer or another
parallel Intake consumer. A valid compaction Item follows the ordinary
notification path and fails through the Projection; a malformed or
uncorrelated compaction may close at the lower Client boundary.

The closed normalized union includes only the lifecycle meaning needed by the
Observer, for example:

```text
THREAD_STARTED
TURN_STARTED
MESSAGE_STARTED
MESSAGE_COMPLETED
REASONING_OBSERVED
USER_MESSAGE_OBSERVED
STREAM_PROGRESS
TURN_COMPLETED
BENIGN_PROCESS_PROJECTION
FORBIDDEN_EFFECT_OBSERVED
PROTOCOL_VIOLATION
```

The exact implemented union and classification table are frozen in Slice 0 and
covered by the new Adapter version and tests; M2.5.1 adds no separate persisted
projection authority. These events remain Adapter-local protocol projections.
They are not Domain, Runtime, Store, Audit, Evidence, Admission, Start, or
Acceptance authority and must not expose Codex DTOs outside the Adapter.

The projection must minimize each event before the Observer receives it:

- lifecycle events carry only bounded IDs, stage, allowed phase, safe counts,
  and the exact validated terminal/message value required for response binding;
- started message projection may carry an empty bounded text value or only its
  byte count because progressive content is not terminal output;
- completed message and terminal projections may carry bounded content only in
  operation memory until response validation and the existing retention policy
  decide the result;
- reasoning and stream progress carry no reasoning or delta text;
- process projections carry only a closed kind and safe status token; and
- forbidden/protocol-violation events carry only a closed reason and bounded
  diagnostic token, never the raw payload.

A known method whose params fail its exact Projection decoder maps directly to
`PROTOCOL_VIOLATION` and never reaches the Classifier.

`IntakeEffectClassifier` is a private pure part of the Projection boundary. It
receives only a closed, already validated, content-minimized protocol fact and
owns its exhaustive effect disposition; it does not receive
`AppServerNotification`, raw params, or lower-client errors independently:

- `remoteControl/status/changed` maps to `BENIGN_PROCESS_PROJECTION` only when
  the exact pinned shape proves remote control remains disabled;
- `account/rateLimits/updated` is schema-validated and maps to a content-free
  benign projection without retaining account values;
- known deprecated Web Search notices are eliminated by removing their source
  keys, not by accepting arbitrary `deprecationNotice` payloads;
- `rawResponseItem/completed` retains its validated inner discriminator only:
  an assistant-role `message` maps to content-free `STREAM_PROGRESS`,
  `reasoning` maps to content-free `REASONING_OBSERVED`, and no raw content is
  forwarded;
- raw collaboration, shell, function, tool-search, custom-tool, Web Search,
  image-generation, or corresponding output variants map to
  `FORBIDDEN_EFFECT_OBSERVED`;
- command, file change, image, MCP, dynamic tool, approval, enabled-effect, and
  other effect-bearing Item activity maps to
  `FORBIDDEN_EFFECT_OBSERVED`; and
- `thread/compacted`, a `contextCompaction` Item, every raw compaction variant,
  raw `other`, and any validated deprecation, warning, reroute, non-disabled
  remote-control, or otherwise unclassified lifecycle fact maps to
  `PROTOCOL_VIOLATION`.

Compaction is a prohibited lifecycle observation, not an effect-bearing Item.
It MUST have the single `PROTOCOL_VIOLATION` disposition above and MUST be
excluded from the generic forbidden-effect branch.

An unsupported method, malformed envelope, lower-client protocol-limit or
correlation failure, and a projected `PROTOCOL_VIOLATION` all close the complete
Intake operation as `ASSISTANT_PROTOCOL_ERROR`. They retain their owning layer
for tests and safe diagnostics; no test may use an unsafe cast to pretend that
the Projection received a method rejected by the lower Client.

`IntakeProtocolObserver` consumes only normalized events. It owns Thread/Turn
correlation, lifecycle order, notification/event budgets, completed-message
uniqueness, terminal-summary binding, and the final response handoff. It does
not switch over raw Codex methods or decide whether a new upstream method is
benign.

Agent-message projection and observation remain stage-aware:

- started messages require exact fields, a valid identity/phase, null citation,
  and a bounded string that may still be empty;
- completed and terminal messages continue requiring non-empty bounded content;
  and
- exactly one completed final message must digest-match the one-item terminal
  summary.

A `FORBIDDEN_EFFECT_OBSERVED` or `PROTOCOL_VIOLATION` event interrupts the bound
Turn when possible, discards all assistant output, closes the owned process,
and creates no Intake authority from that output. No projection may convert an
unknown event into a benign event by default.

Diagnostics may retain only the normalized closed category, bounded token,
lifecycle location, and count. They must not retain notification payloads, user
or model content, account values, authentication material, hidden reasoning, or
raw exceptions.

## 8. Trusted real Execution Profile composition

The current production Intake composition installs `profile_m1-happy-path` and
uses `FakeWorker`, `FakeCandidateSource`, and `FakeVerificationRunner`. The
existing protected M2 demonstration is also a mixed test composition: its
external Codex Profile selects only `IMPLEMENT`, while its candidate-free
`DISCOVERY` and `PLAN` delegate to `FakeWorker`. Neither composition is the
formal M2.5.1 product chain.

M2.5.1 MUST remove the M1 Profile as an implicit ordinary-production fallback
and MUST NOT relabel the existing mixed demonstration as an all-real path. The
bounded supported composition must receive one exact trusted real Profile with
this closed phase mapping:

| Workflow phase | Formal Worker | Filesystem/effect boundary |
| --- | --- | --- |
| `DISCOVERY` | real Codex, candidate-free | exact Runtime-owned selected-source snapshot is read-only; checkout is unreadable; no Candidate |
| `PLAN` | real Codex, candidate-free | exact Runtime-owned selected-source snapshot is read-only; checkout is unreadable; no Candidate |
| `IMPLEMENT` | real Codex, Candidate-bound | exact current mutable controlled-copy Candidate and allowed paths only |
| `SOURCE_FREEZE` onward | no coding Worker | existing Candidate, Verification, Evidence, and Acceptance owners |

The candidate-free invocation MUST receive only the phase-specific Context and
the exact single-Attempt read-only snapshot identity frozen by Slice 0. Trusted
workspace composition materializes only the admitted ADR 0029 selected-file
projection below a separate Runtime-owned project-read root. The source
checkout, `.git`, ignored or projection-excluded paths, Candidate roots,
authority, credentials, protected assets, and sibling snapshots remain
unreadable. The snapshot is not a Candidate and cannot become mutable or enter
Evidence/Acceptance identity.

The invocation MUST NOT receive a Candidate lease, Candidate digest, Store
capability, source-write capability, or authority to persist its proposals. Its
output remains the existing phase-allowed untrusted `PROPOSALS` result.
`IMPLEMENT` continues to receive the current mutable Candidate lease and may
emit only the existing completion-request result. Real failure in any selected
Worker phase fails closed; it MUST NOT fall back to `FakeWorker` or advance the
Workflow through synthetic output. This project read occurs only after formal
Goal creation and ordinary Start inside Goal-bound Workflow phases. It is not
pre-Goal project-assisted Intake, ambient Intake tool use, or the full M3
relevance/Fact selection system.

`FakeWorker`, `FakeCandidateSource`, and `FakeVerificationRunner` remain
available for their accepted deterministic regression, fixture, failure-
injection, and offline test roles. They MUST be reachable only through explicit
test composition and MUST NOT appear in the formal Profile, phase resolver,
mandatory live path, or live receipts.

After ADR 0043 is accepted, implementation MUST add its immutable candidate-
free project-read authority, exact owned snapshot materialization, Context
binding, additive `ExternalExecutionProfileDefinitionV3` phase-dispatch
definition, additive `ExternalExecutionIntentV2`/`ExternalExecutionRecordV2`,
`CodexWorkerDirectiveV3`, and `CodexAdapterObservationV2`, and strict
persistence/reopen support. Each `DISCOVERY`/`PLAN`
Attempt atomically retains the exact read authority and snapshot root with
Context and Attempt start before dispatch, rechecks both source and snapshot
before the Turn and after it ends, and admits no proposal after drift. The
External Execution intent binds that snapshot as cwd.

Because snapshot materialization necessarily precedes that atomic commit,
startup reconciliation MUST use a monotonically sequenced Runtime-issued
Store-authority snapshot. The workspace port may classify an exact externally
owned marker-bound leaf but cannot authorize deletion. Runtime may persist a
consume-once cleanup grant only for a terminal committed snapshot or an exact
owned orphan whose preallocated record identity is absent from that authority
snapshot and has no active consumer. Ambiguous, aliased, unowned, or merely old
leaves remain visible and are never deleted by naming or age inference.

The cleanup grant is the sole operation identity. Until one immutable Cleanup
Outcome exists, it remains unresolved and no replacement grant may be issued.
The workspace port makes invocation by that exact grant idempotent across
sequential retries and simultaneous calls from separate processes or Store
connections. It keeps the exact grant-bound leaf as the only cleanup target and
uses a deterministic grant-derived internal operation identity plus an atomic
filesystem claim or equivalent process-safe mechanism. Competing calls may
join only that same logical operation, cannot select another leaf, and cannot
return a terminal observation while the operation can still mutate the
filesystem. This does not add a Host lease, heartbeat, time-based takeover, or
second Runtime grant. The port returns `ALREADY_ABSENT` when deletion completed
before a crash but its result did not commit. Runtime atomically persists the
strictly decoded Outcome, audit, and grant consumption. Concurrent Outcome
writers serialize:
one valid observation authors the retained Outcome and every loser returns it
instead of persisting its local observation. A retained Outcome replays without
another port call; restart with an unknown result may invoke only the same
unresolved grant.

Request handling follows one closed matrix before any port effect: replacement-
grant issuance and missing, caller-authored, naming-derived, or age-derived
grant/target admission are rejected; exact resolved-grant replay returns the
retained Outcome; grant-identity reuse with different canonical content returns
an identity conflict; and only the exact unresolved grant may invoke or
reconcile the logical operation. Every rejection, replay, and conflict path
calls no port and creates no new Cleanup Outcome.

Any additional Adapter coordination state is non-authoritative, exact-grant-
and-marker-bound, outside the readable snapshot, and contained by the already
bound Runtime-owned project-read workspace root. While the grant is unresolved,
crash recovery may interpret or continue that state only for the same grant
without naming- or age-based discovery. If the post-effect target state cannot
be stably classified as absent or present-and-retained, or coordination
finalization cannot be proven, the port returns no terminal observation and the
same grant remains unresolved for same-grant reconciliation. A terminal
observation leaves no active coordination capability and states only the
current proven observation: `DELETED` means this logical operation safely
deleted the exact leaf; `ALREADY_ABSENT` observes it absent without attributing
cause; `RETAINED_UNSAFE` observes and leaves untouched a present replacement,
alias, ambiguity, or partial residual without attributing earlier effects; and
`FAILED` proves failure before any target effect plus an exact matching terminal
reobservation. A terminal reobservation that instead finds absence maps to
`ALREADY_ABSENT`, a stable present unsafe/partial target maps to
`RETAINED_UNSAFE`, and an unclassifiable target leaves the grant unresolved.
An internal operation/coordination identity or state conflict also leaves the
same grant unresolved even when the target alone appears stable.
`DELETED` or `ALREADY_ABSENT` requires every additional persistent coordination
artifact removed. `RETAINED_UNSAFE` or `FAILED` may retain such artifacts only
visibly as inert closed-failure material; after resolution they may be
inspected but never continued.

`PLAN -> IMPLEMENT` MUST compare the Candidate Source projection with the
current admitted Plan source authority and create no Candidate on mismatch. A
mismatch records `PLAN_SOURCE_NOT_CURRENT`, preserves the completed PLAN
Attempt, and atomically moves the Workflow from `PLAN / READY` to
`PLAN / FAILED` through existing Workflow integrity-failure authority. It stops
without an automatic retry, replacement PLAN Attempt, phase rewind, or
`goal resume` continuation. The exact enum-backed code is persisted as the
Workflow integrity event `reason` and resulting Workflow `suspendedReason`; the
Store rechecks the event, Workflow, audit, and processed-command relationships,
and public status exposes it as `detailCode`. The Workflow failure projects the
Goal to `BLOCKED / INSPECT_BLOCKER`, not a resumable recovery catalog. The user
must create a new Goal against the changed source; restoring the previous bytes
does not revive the failed Workflow.

Existing M1/M2 Profile and Context records retain their original identities and
semantics.

The nested v3 projection MUST separate genuinely shared execution fields from
phase-owned fields; a phase-owned value MUST appear only in its
`phaseDispatch` entry, and a duplicate global form is invalid rather than a
precedence choice. Each entry MUST bind phase, adapter, cwd/source kind,
permission/isolation identity, project-configuration activation policy, exact
configuration/execution/disabled-integration digests, automatic instruction-
source manifest, capability and response contracts, Adapter-local Worker
activity-policy ID/digest, network/approval/
continuity/compaction/fallback policy, and allowed/forbidden roots. V3 fixes
`workerDispatchPolicy = ALL_SELECTED_ATTEMPTS`; its declared
phase set and entries use the current canonical string order `DISCOVERY`,
`IMPLEMENT`, `PLAN`. Workflow Runtime, not this array, drives the actual
`DISCOVERY -> PLAN -> IMPLEMENT` sequence. Project configuration and
integrations remain disabled; automatic instruction discovery or an unbound
instruction source fails closed.

The installed phase `allowedRoots` are stable workspace-root envelopes, not
dynamic Attempt leaf paths. The exact project-read snapshot leaf remains owned
by its `ProjectSourceReadAuthorityRecord`; the exact Candidate leaf remains
owned by its workspace lease. Trusted composition MUST require each exact leaf
and its workspace root to be contained by a selected Profile envelope, compute
effective allowed access as the phase/source intersection, and compute
effective forbidden access as the union of phase and source-authority roots.
String-prefix comparison is not containment. Every phase MUST include the
shared controlled-state root in its forbidden set. The Adapter's supported
isolation ID/digest is derived from the complete phase isolation contract, and
its disabled-integration digest binds the exact `0.146.1` Worker feature-denial
projection without reusing the historical `0.146.0` list.

The Worker activity policy is Adapter-local and versioned; Domain and Runtime
bind only its protocol-neutral opaque identity. Trusted composition
deterministically selects the one supported v1 Adapter policy for the exact
phase entry and verifies that it is a strict refinement of the canonical
Domain capability grant and response contract: candidate-free grants permit
only proposal-producing snapshot reads, while the `IMPLEMENT` grant is the
only mapping that can admit Candidate-lease-bound commands and file changes.
Profile values outside the Domain grant, including cwd/root, network, approval,
integration, instruction, continuity, and compaction policy, remain separately
fixed by the same phase entry and effective isolation. The Adapter policy may
narrow those combined permissions but cannot widen any of them.

The policy separately admits bounded non-effect lifecycle and terminal
observations, snapshot-cwd read commands for `DISCOVERY`/`PLAN`, and Candidate-
lease-bound commands/file changes for `IMPLEMENT`. File changes in a candidate-
free phase, activity outside the exact cwd/lease/allowed roots, approvals,
network or integration effects, unknown Items/effects, and phase-policy,
capability-grant, response-contract, or effective-isolation mismatch discard
the Worker result and fail closed. `CodexWorkerDirectiveV3` and
`CodexAdapterObservationV2` repeat the exact selected policy binding; neither
the policy nor observation becomes Workflow or Acceptance authority, and no
separate compatibility authority record is introduced.

[ADR 0044](../adr/0044-source-freeze-owned-candidate-change-containment.md)
closes the remaining distinction between an unknown Item/effect and the pinned
protocol's best-effort `unknown` command-action parse. Candidate-free phases
continue to reject that action. `IMPLEMENT` may admit it only when the exact
Candidate lease/cwd and effective isolation are followed by Candidate Manager-
owned schema-version-2 source-freeze proof. That proof canonically compares the
persisted base manifest with two stable current manifests, records exact added,
modified, and deleted regular-file identities, and lets Runtime independently
require every changed path to equal or descend from the Goal's exact
`allowedPaths`. The Runtime/Store validation, SQLite relationship backstop, and
Evidence composition are now installed,
so the Adapter-local policy admits that best-effort action only for
`IMPLEMENT`; the later freeze remains mandatory and a failed containment check
invalidates the Candidate without freeze Evidence. An early `fileChange`
rejection does not replace the black-box manifest proof, and the installed
offline foundation is not a `M251-C11` acceptance verdict.

The v2 Intent/Record and v3 Codex directive/Adapter observation use one
phase-discriminated source union: project-read record/snapshot for
`DISCOVERY`/`PLAN`, Candidate lease/cwd for `IMPLEMENT`. The Adapter-local v3
ProjectRead member carries the complete decoded retained record, recomputes its
canonical digest, and reduces it to ID/digest/cwd only when constructing its
observation and final-result bindings; that reduction is not a second authority
record. Historical Intent/
Record v1 retain their phase-conditional Candidate semantics without gaining
project-read fields; Codex directive v2 and Adapter observation v1 retain their
Candidate-bound `IMPLEMENT` meaning. Lifecycle `ExternalExecutionObservationV1`,
`WorkerRequestV2`, `WorkerEventV1`, and `WorkerEventReceiptV1` remain unchanged
only after Slice 0 proves their digest/Context bindings already cover both
source members; otherwise the changed boundary receives a new additive version.

Implementation MAY extract reusable pieces from the protected-demo proof, but
MUST NOT import its scenario-specific assembly or its FakeWorker
`DISCOVERY`/`PLAN` delegation into the product path. Before publishing Intake
or Goal handlers, trusted composition must:

1. verify the supported Codex binary, protocol snapshot, auth source,
   controlled roots, source-project containment, and configured project-read,
   Candidate-workspace, authority, credential, protected-asset, and temporary-
   root separation;
2. install the exact external-backend capability record;
3. install one versioned Execution Profile binding the exact phase-to-Worker
   mapping, candidate-free snapshot and cleanup boundary, per-phase
   configuration/instruction/response policy, candidate-bound Codex Adapter,
   controlled-copy Candidate source, Context/dispatch policy, verification
   family, and protected assets;
