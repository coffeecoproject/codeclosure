# M2.7 Local Runtime Host and Single-Goal Project Control implementation plan

- Status: Draft; formal decisions are proposed and implementation has not
  started
- Plan date: 2026-08-06
- Milestone: M2.7
- Milestone boundary: [CodeClosure milestones](../milestones.md#m27--local-runtime-host-and-single-goal-project-control)

- Milestone assessment: [M2.7 acceptance plan](m2.7-acceptance-plan.md)

## 1. Purpose and completion meaning

This plan sequences a bounded local Runtime Host after M2.6. The Host keeps
existing governed Goal execution alive when the visible CLI detaches, permits a
later CLI to reconnect, gives one CLI writable project control while other
clients are observers, and enforces one started non-terminal Goal per exact
project through the shared Start/Store boundary.

M2.7 is not a scheduler. Ready Goals do not form a queue and are never started
automatically when the project slot becomes free.

Creating this plan does not implement or accept M2.7. Slice completion would
produce an assessment candidate only. The milestone requires the canonical
zero-skip procedure and an independent dated unconditional verdict.

## 3. Entry conditions

M2.7 implementation MUST NOT begin until:

1. M2.6 has passed its own independent bounded completion review;
2. ADR 0040 through ADR 0042 have accepted dispositions;
3. exact local transport, endpoint, Host lock/process identity, epoch, lease
   renewal/expiry, shutdown deadline, and migration policies are closed;
4. the complete M1/M2/M2.5/M2.6 regression baseline is green on the base
   revision;
5. retained databases with zero, one, and conflicting historical active Goals
   have explicit migration outcomes;
6. the deterministic Host/CLI/Worker fixtures and process-control failure seams
   exist through trusted proof composition;
7. this plan and acceptance plan are indexed and the assessed branch/base state
   is recorded; and
8. no higher-authority conflict or hidden scheduling scope remains.

Read-only probes and planning may occur earlier but are not implementation.

## 4. Fixed scope

The bounded implementation includes:

- durable `RuntimeHostRecord`, monotonic `HostEpoch`, closed lifecycle, exact
  process/launch/endpoint identity, and single-owner bootstrap;
- versioned bounded local control transport and compatible CLI attachment;
- Host-owned Store activation, M2.6 Interaction reconciliation, existing
  Runtime recovery, and public capability publication;
- durable `ProjectControlLease`, monotonic `ControlEpoch`, renewal/expiry,
  normal release, and strict stale-client rejection;
- one writable controller and bounded read-only observer clients for each exact
  principal/project;
- durable `ProjectExecutionSlot` acquired atomically by first Start and
  released atomically only by Goal close/cancel;
- shared typed `PROJECT_EXECUTION_SLOT_OCCUPIED` Start rejection and read-only
  start-eligibility projection;
- Host-owned Goal execution after CLI detach and reconnect to exact state;
- graceful Host shutdown plus abrupt crash/restart reconciliation; and
- deterministic concurrency, migration, failure-injection, cross-process,
  strict-reopen, and bounded live proof.

## 5. Explicit non-scope

M2.7 does not implement:

- a waiting Goal queue, priority, fairness, or automatic next-Goal selection;
- automatic Start when a project slot becomes free;
- two writable CLIs, manual lease transfer, or collaborative editing;
- multiple active Goals per project or parallel Goal workers;
- global machine-wide scheduling across projects;
- multi-user/team, remote client/worker, or cloud behavior;
- project-aware ordinary conversation, Fact Graph, or Goal Revision;
- automatic repair/retry changes;
- rich notification/Human Decision UX or broad privacy/retention work;
- technical Acceptance changes; or
- promotion, merge, release, deployment, or another external effect.

## 6. Slice sequence

### Slice 0 — Host, lease, slot, and proof decision closure

Deliverables:

- accept, replace, or reject ADR 0040 through ADR 0042;
- fix local transport and endpoint security/framing/size/deadline identities;
- fix Host lock, process identity, launch nonce, compatibility, epoch, startup,
  drain, and shutdown policies;
- fix control-lease renewal, expiry, observer capability, and stale-client
  rules;
- fix slot acquisition/retention/release, occupied-result, migration, and
  public-view contracts; and
- freeze the M2.7 assessment matrix and source-evidence contract.

Exit evidence:

- no daemon, lease, slot, or migration behavior remains an implicit fixture
  choice;
- no item adds scheduler or M2.5 delayed-start authority; and
- read-only probes are clearly labelled non-implementation evidence.

### Slice 1 — Host/lease/slot Domain and ports

Deliverables:

- branded identities and closed records for Host, Host Epoch, client, control
  lease/epoch, and project slot;
- owning codecs and canonical projections/digests with golden vectors;
- closed local transport request/response DTOs and typed errors;
- public application port extensions without Store/kernel leakage; and
- invariants separating Host, control lease, slot, Workflow, and Acceptance.

Required proof:

- malformed, partial, stale, unknown-field, cross-home/project/principal, and
  digest-substituted values fail closed;
- Codex/backend protocol types do not enter the new records/ports; and
- no Host/lease/slot value can issue Workflow or Acceptance authority.

### Slice 2 — SQLite Host, lease, and slot authority

Deliverables:

- append-only migrations and schema fingerprint updates;
- compound Host publication/stop, lease acquire/renew/release/expire, slot
  acquire/release, command outcome, and audit transactions;
- migration preflights for retained non-terminal started Goals;
- immediate-read and strict close/reopen validation; and
- failure injection at every compound-write boundary.

Required proof:

- two active Hosts, two control leases, or two slots for one scope cannot
  persist;
- migration never chooses a winner from ambiguous historical Goals;
- state/audit/outcome/slot relationships are atomic; and
- offline corruption fails strict reopen.

### Slice 3 — Runtime Host bootstrap and local transport

Deliverables:

- exact single-owner OS lock/endpoint bootstrap;
- Host process launch, compatibility handshake, Host Epoch publication, health,
  drain, clean stop, and forced-cleanup boundaries;
- bounded versioned local transport adapter/client;
- Store activation and all recovery before capability publication; and
- deterministic fake Host/process/transport fixtures.

Required proof:

- concurrent startup, endpoint spoof, PID reuse, stale epoch, incompatible
  version, partial startup, and failed recovery all fail closed;
- clients never receive raw Store or internal kernel capability; and
- transport replay cannot duplicate a Runtime command.

### Slice 4 — Attach, control lease, and observer mode

Deliverables:

- CLI attach/start/reconnect composition;
- controller lease acquire/renew/release/expiry and Control Epoch validation;
- M2.6 Interaction Session relocation into the Host;
- observer Goal list/status/audit/result surface; and
- closed rejection of observer conversation and mutation attempts.

Required proof:

- one controller and any bounded number of observers attach consistently;
- normal detach releases only the lease;
- abrupt detach cannot let old and new control epochs mutate concurrently; and
- observer mode cannot create indirect pending-action or assistant work.

### Slice 5 — Shared project execution slot

Deliverables:

- slot-aware public/Store Start contract and typed occupied result;
- atomic first Start plus slot acquisition across every execution profile;
- owner-preserving Resume and atomic close/cancel release;
- public start-eligibility/occupant summary; and
- direct CreateGoal plus M2.5 Materialization/automatic-Start composition.

Required proof:

- concurrent Starts in one project yield one owner and one typed loser;
- different projects may start independently;
- every non-terminal owner state retains the slot;
- non-owners remain ordinary `READY` Goals and never auto-start; and
- M2.5 Start failure leaves committed Materialization visible and replay-safe.

### Slice 6 — Detached Goal execution and reconnect

Deliverables:

- Host-owned Goal task registry derived from Runtime authority;
- CLI detach while one governed Goal remains active;
- later CLI reconnect and exact status/result projection;
- bounded Host notifications independent of client presence; and
- no-client execution/recovery lifecycle proof.

Required proof:

- closing the sole CLI persists no `CancelGoal` and does not stop Host-owned
  execution;
- reconnect reads exact current authority without conversation reconstruction;
- a detached correct first-pass Goal may close only through existing Evidence
  and Acceptance; and
- absent clients grant no extra retry, repair, or scheduling authority.

### Slice 7 — Crash, recovery, concurrency, and strict reopen

Deliverables:

- abrupt Host/client/Worker interruption fixtures;
- process identity, endpoint, Host/Control Epoch, lease, slot, and external-
  execution reconciliation;
- retained-slot migration adversaries;
- cross-process controller/observer/Start races; and
- resource cleanup with bounded logs/output/deadlines.

Required proof:

- Host crash is not Cancel, closeout, slot release, or automatic redispatch;
- a new Host publishes only after exact prior-owner and Runtime recovery;
- ambiguous surviving process identity remains blocked;
- stale clients cannot mutate after Host/control epoch change; and
- no queue or automatic next Goal appears after recovery or slot release.

### Slice 8 — Canonical assessment and independent review

Deliverables:

- fail-closed non-verdict `accept:m2.7` runner;
- exact source manifest and sole later-review exclusion;
- zero-skip execution of every mandatory row;
- full M1/M2/M2.5/M2.6 regression on the assessed source; and
- independent dated completion review with one unconditional or failed bounded
  verdict.

The runner cannot issue the milestone verdict.

## 7. Required walking demonstration

The deterministic demonstration must show:

1. CLI A starts or attaches the sole compatible Host and acquires control for
   one principal/project;
2. a clear M2.6 natural-language request materializes and starts Goal A;
3. the first Start atomically acquires the project slot;
4. CLI B attaches as observer, reads Goal A status, and cannot mutate anything;
5. CLI A detaches without `CancelGoal`, while Host-owned Goal A continues;
6. a later CLI obtains a new Control Epoch and sees exact current Goal A state;
7. Goal B may exist in `DISCOVERY / READY`, but Start while A owns the slot
   returns `PROJECT_EXECUTION_SLOT_OCCUPIED` and creates no execution;
8. Goal A closes or is cancelled and releases the slot atomically;
9. Goal B remains unchanged and is not automatically started; and
10. only a fresh user-authorized `StartGoal` for Goal B acquires the free slot.

Supplementary cases cover Host crash/restart, stale endpoint/epoch, abrupt
controller loss, observer mutation attempts, occupied M2.5 automatic Start,
slot-release failure injection, conflicting retained migration state, different
projects, notification loss, and correct first-pass execution.
