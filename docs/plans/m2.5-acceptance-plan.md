# M2.5 Goal Intake and Materialization acceptance plan

- Status: Implementation in progress; Slices 1 through 3 complete; milestone acceptance not executed
- Plan date: 2026-08-02
- Milestone: M2.5
- Implementation plan: [M2.5 Goal Intake and Materialization implementation plan](m2.5-goal-intake-materialization.md)
- Milestone boundary: [CodeClosure milestones](../milestones.md#m25--goal-intake-and-materialization-vertical-slice)

## 1. Purpose

This document defines the independent, executable exit assessment for the
bounded M2.5 Goal Intake and Materialization vertical slice. It converts the
required demonstration, exit criteria, and adversarial cases into one
zero-skip verdict matrix over an exact source identity.

This plan is not an implementation record and does not issue Admission,
Materialization, Start, technical Acceptance, merge, release, deployment, or
product-completion authority. Creating it does not advance implementation or
acceptance. M2.5 may be described as implemented only after its slices are
complete, and it is not accepted until every mandatory row has passed and an
independent dated review records one unconditional verdict.

## 3. Acceptance question and bounded claim

The reviewer answers exactly this question:

> Does the exact reviewed source implement the bounded M2.5 path from an
> immutable Raw Request through source-bound deterministic Intent Admission to
> atomic Goal Materialization and separately authorized ordinary Start, while
> preserving all M1/M2 authority boundaries, deterministic replay, strict
> restart recovery, and fail-closed adversarial behavior?

An unconditional `PASS` proves only that bounded claim. It does not prove:

- project-assisted Intake or broad repository discovery;
- automatic Goal revision or complete requirements understanding;
- a long-lived conversation router or Thread-memory subsystem;
- rich TUI, complete Human Decision UX, multiple Intake agents, or model
  voting;
- complete Fact Graph, business knowledge, privacy, or erasure capability;
- arbitrary-project verification completeness or product completion; or
- merge, release, deployment, communication, purchase, or another external
  effect.

## 4. Entry conditions

The assessment MUST NOT start until:

1. the [M2 completion review](../reviews/m2-completion-review.md) remains an
   unconditional `PASS`;
2. every M2.5 Slice 0 through 7 implementation deliverable is complete with
   focused evidence, while no Slice or runner has claimed the milestone verdict;
3. the working tree and exact source identity are recorded before execution;
4. Node and pnpm satisfy the repository manifest and lockfile;
5. every migration through the final M2.5 migration exists and a fresh database
   can be created;
6. the installed Intake Admission Policy, Intake assistant profile, Workflow
   Policy, and Execution Profile identities are fixed and recorded;
7. the deterministic App Server fixture and bounded failure-injection controls
   are available through public test seams;
8. the canonical `accept:m2.5` command exists, names every mandatory executable
   stage, and declares only
   `docs/reviews/m2.5-completion-review.md` as its narrow self-referential source
   exclusion;
9. ADR 0034's Intake command and verified-activation contracts are implemented
   without a lower-authority reinterpretation; and
10. there is no unresolved higher-authority conflict or unreviewed scope change.

If an entry condition cannot be established, the result is `BLOCKED`, not a
partial pass.

## 5. Canonical execution procedure

The M2.5 implementation MUST add one root command:

```text
corepack pnpm accept:m2.5
```

The command MUST run non-interactively and fail closed. It MUST record, in one
machine-readable evidence directory:

- opening and closing source identity, branch, working-tree state, platform,
  architecture, Node version, pnpm version, and SQLite/runtime versions;
- exact command list, start/end time, exit code, duration, skip count, and
  artifact digest for each stage;
- the installed policy/profile/adapter/schema identities used by the proof;
- isolated authority database and state roots for every scenario;
- scenario input identity and final safe authority projection;
- close/reopen results and expected-versus-observed disposition; and
- one final executable-assessment result that is `PASS` only when every
  mandatory executable stage and row passed and the closing source identity
  equals the opening identity.

At minimum the canonical command MUST compose these stages in this order:

1. source, toolchain, lockfile, generated-artifact, and clean-scope preflight;
2. formatting, lint, strict type checking, package tests, dependency checks,
   migration tests, invariant tests, and documentation checks;
3. the complete M1 acceptance procedure;
4. the complete M2 acceptance procedure, using its required bounded live
   prerequisites where the accepted M2 procedure requires them;
5. M2.5 static authority and dependency proof;
6. M2.5 deterministic assistant/adapter proof through the real lower App
   Server client;
7. M2.5 real SQLite transaction, failure-injection, concurrency, and strict
   reopen proof;
8. M2.5 real CLI cross-process demonstration; and
9. source-identity closure and evidence-manifest validation.

The runner MUST reject an omitted, filtered, quarantined, retried-to-green,
expected-failure, or zero-test stage. It MUST NOT rewrite the source, database,
fixture, policy, profile, or expected result while deciding the verdict.

The runner's `PASS` means only that the executable evidence is ready for
independent review. It is not the M2.5 milestone verdict and cannot update
milestone status.

## 6. Proof architecture

### 6.1 Deterministic mandatory evidence layer

The mandatory executable assessment uses a controlled App Server fixture
through the real `packages/codex-app-server-client` process/protocol path and
the real M2.5 Intake Adapter. Fixed assistant output remains untrusted input;
Runtime validation, deterministic Admission, SQLite compound transactions,
Goal Manager, Workflow Runtime, and ordinary `StartGoal` produce authority.

This layer MUST prove exact Proposal and Answer payloads, timeouts, protocol
errors, Compact, Thread loss, process exit, interrupted streams, malformed
responses, and unsupported server requests without model nondeterminism.

The installed local-v1 Admission Policy has exactly empty `POLICY_DENIED` and
`UNSUPPORTED` rule collections. Rows requiring those accepted Decision variants
use only the two exact non-default deterministic test Policies fixed in the
implementation plan; evidence MUST prove their IDs, versions, canonical
digests, sole additional structured predicates, and absence from local CLI
composition. The runner cannot add or rewrite a rule while deciding a result.

### 6.2 Real persistence and process layer

Each persistence scenario MUST use the production SQLite Store, production
migrations, production codecs, and real close/reopen. CLI rows MUST use separate
OS processes against one isolated authority home so an in-memory pass cannot
substitute for restart proof.

Fault injection may select a named transaction boundary. It MUST NOT bypass
the production transaction implementation or insert an otherwise impossible
authoritative state through public APIs.

### 6.3 Optional live observation

A bounded live Codex Intake observation MAY be recorded after all mandatory
deterministic rows pass. Its semantic Proposal or Answer is not prescribed, it
cannot authorize a Goal by itself, and it is not verdict-critical unless the
M2.5 milestone and this plan are explicitly amended before execution.

Unavailable credentials, network, or model service therefore do not block the
new M2.5 semantic proof. They do not waive any live prerequisite already owned
by the accepted M2 regression procedure.

## 7. Evidence and isolation requirements

Every mandatory scenario MUST:

- start from an isolated temporary authority home, database, adapter state
  root, Candidate root, and controlled project fixture;
- use deterministic IDs and a causal Runtime clock where the scenario requires
  exact equality;
- record the Raw Request, Manifest, Proposal, Projection, Source Bindings,
  ambiguity, Question, Clarification Answer Binding, Decision, command
  reservation/outcome, presence or absence of
  `abandonClarificationBinding`/`AbandonmentBinding`, Materialization, optional
  Start Authorization, Goal/Workflow/Attempt references, and audit identities
  that are expected to exist;
- assert absence, not merely non-display, for authority that MUST NOT exist;
- inspect both the immediate read and strict close/reopen projection;
- prove audit and state were committed together;
- prove the adapter and CLI used only public Runtime surfaces; and
- redact secrets, private reasoning, transcript bodies, raw exceptions, and
  unrestricted user content from evidence artifacts.

Exact semantic equality MUST use canonical digests and closed typed
dispositions, not path existence, log substrings, model prose, or object count
alone.

## 9. Failure-injection requirements

The harness MUST expose named deterministic injection points before and after
every authoritative write in these compound operations:

- Raw Request/IntakeRun/command reservation;
- `CLARIFY` Decision/Question/active-reference compound write and later
  clarification Raw-Request/Answer-Binding/current-reference compound write;
- `ABANDON_CLARIFICATION` reservation/Decision/active-reference/outcome
  compound write;
- immediate no-external reservation/Decision/terminal status/audit/outcome;
- Proposal/Projection/Source Binding/ambiguity/Decision;
- Answer-only Decision/Response/status/audit/outcome;
- terminal Failure/status/audit/outcome;
- Admission/Goal/Workflow/Materialization/Start Authorization/audits/outcome;
  and
- ordinary first Start Policy/Profile/Context/Attempt/dispatch preparation.

For writes that belong to one Store transaction, every injected failure MUST
leave none of that transaction's new authority. For the intentionally separate
Materialization and Start transactions, failure MUST preserve the committed
Goal as visible `READY`, never roll it back, and never imply an Attempt or
dispatch that did not commit.

## 10. Verdict rules

The executable runner may report `PASS`, `FAIL`, or `BLOCKED` for its evidence
procedure, but runner `PASS` means only `READY_FOR_INDEPENDENT_REVIEW`. It is not
a milestone status change, technical Acceptance, or completion authority.

The later independent review may issue only:

- `PASS` — every entry condition and mandatory row passed on one exact source
  identity, with no skip, waiver, expected failure, semantic retry, or material
  unexplained warning;
- `FAIL` — execution completed far enough to establish that one or more
  mandatory contracts are false; or
- `BLOCKED` — the assessment cannot validly execute because an entry condition,
  environment prerequisite, exact source identity, required M2 regression
  prerequisite, or evidence layer is unavailable.

`BLOCKED` is not a milestone pass. A conditional pass, partial pass, risk
acceptance, follow-up TODO, or “pass except” verdict is prohibited.

The review MUST identify every failed or blocked executable matrix row, the
exact command and artifact, whether any source changed during execution, and
the next required authority-preserving action. It MUST distinguish document
completion, implementation completion, milestone completion, and product
completion.

## 11. Review record

After the canonical procedure reports executable `PASS`, a reviewer independent
from the implementation sequence MUST inspect the complete output, actual diff,
working-tree status, isolation/effect trace, and evidence manifest before
creating:

```text
docs/reviews/m2.5-completion-review.md
```

The acceptance runner MUST have declared that exact review path as its only
self-referential source exclusion before execution. The exclusion permits the
review to describe already-fixed product, fixture, schema, configuration, test,
and documentation input; it does not permit any other source change.

After writing the review, the complete offline quality gate, documentation
checks, source-manifest validation, `git diff --check`, and semantic scope review
MUST rerun on the review-bearing tree. The preceding M2.5 executable evidence
and mandatory M2 live-regression evidence may be referenced only when the
declared exclusion proves that no non-review source or input changed. Otherwise
the complete canonical M2.5 assessment reruns on the new source identity.

The record MUST contain:

1. exact source and environment identity;
2. reviewed authority sources and accepted ADR set;
3. opening and closing working-tree scope;
4. every canonical command and zero-skip result;
5. a result for every executable matrix row;
6. migration, strict reopen, fault-injection, concurrency, CLI, and regression
   evidence references;
7. optional live observation clearly separated from mandatory proof;
8. residual non-claims and later-milestone work; and
