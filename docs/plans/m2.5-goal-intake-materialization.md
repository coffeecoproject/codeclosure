# M2.5 Goal Intake and Materialization implementation plan

- Status: Planned; implementation has not started
- Plan date: 2026-08-02
- Milestone: M2.5
- Milestone boundary: [CodeClosure milestones](../milestones.md#m25--goal-intake-and-materialization-vertical-slice)

## 1. Purpose and completion meaning

This plan translates the accepted M2.5 Goal Intake contract into a bounded
implementation order. It incorporates the implementation-readiness items
reviewed after the M2 exit verdict: Intake persistence, the Intake Assistant
Adapter, Thread policy, deterministic Admission, Materialization and Start
composition, CLI and read views, compatibility, recovery, and adversarial
proof.

This document does not create a second product contract. If it conflicts with
the Runtime invariants, an accepted ADR, the product/architecture contracts, or
[Goal Intake](../goal-intake.md), the higher-authority record wins and
implementation MUST stop until the conflict is resolved.

Completing this document means only that M2.5 has a build and proof sequence.
It does not mean that Goal Intake is implemented, that M2.5 has passed, that a
materialized Goal is technically complete, or that CodeClosure is authorized
to merge, release, deploy, communicate, purchase, or perform another external
effect.

## 4. Fixed scope

The bounded implementation includes:

- immutable Raw Request roots and revisions with exact admitted user content,
  trusted local principal, explicit interaction action, project/scope and
  declared constraints;
- a versioned IntakeRun lifecycle with immutable Proposal, Projection, Source
  Binding, Material Ambiguity, Clarification Question, Clarification Answer
  Binding, Decision, Answer-only, Failure, Materialization, and optional
  Start-Authorization authority;
- a distinct Goal Intake Assistant Adapter over the reusable App Server client;
- separate closed response contracts for Intent analysis and Answer-only;
- a deterministic installed Intent Admission Policy and Engine;
- atomic `CLARIFY`, `NO_EXECUTION`, and `MATERIALIZE` transactions;
- terminal Intake processing failure and restart reconciliation without model
  recall;
- exact pre-Goal command reservation, idempotency, replay, conflict, and
  concurrent-loser behavior;
- atomic Goal revision 1 plus unique `DISCOVERY / READY` Workflow creation;
- optional Goal Start Authorization followed only by a separate ordinary
  `StartGoal` command;
- basic CLI submission, clarification, status, and audit views;
- strict SQLite migration, immediate-read, close/reopen, and corrupted-state
  validation; and
- the full M2.5 deterministic and adversarial acceptance matrix.

The implementation explicitly excludes:

- a long-lived chat or `InteractionSession` router;
- front-door routing among ordinary chat, Intake, Goal status, and control
  requests;
- a front-end Thread epoch or conversation-memory subsystem;
- optional Intake project exploration in the baseline slice;
- broad project/business discovery or full Fact Graph traversal;
- Goal revision after Materialization;
- multiple simultaneous Clarification Questions, batch answers, Question
  lifecycle state machines, or a generic questionnaire engine;
- rich TUI, complete Human Decision UX, Goal scheduling, multiple Intake
  agents, model voting, or multi-Goal Worker concurrency;
- automatic retry of a failed Intake operation;
- technical Acceptance, Candidate Promotion, or external-effect changes; and
- any new M2.6 milestone claim. A later unified front door requires its own
  accepted repository decision and is not inferred from this plan.

## 5. Baseline implementation decisions

### 5.1 Trusted interaction surface

The initial CLI MUST require one visible, explicit action for every new Raw
Request:

- `ANSWER_ONLY`;
- `MATERIALIZE_ONLY`; or
- `GOVERNED_EXECUTION`.

M2.5 defines no implicit CLI default. Conversation continuation, inactivity,
model classification, a detached approval, or user silence cannot supply the
action. The single-user local CLI obtains its principal identity from trusted
composition; it does not accept a caller-supplied `--principal` override.

The planned command surface is:

```text
codeclosure intake submit \
  --action <answer-only|materialize-only|governed-execution> \
  --request <text> [--project <path>] [--constraint <text> ...] [--json]

codeclosure intake clarify <intake-run-id> \
  --question-id <clarification-question-id> \
  --expected-version <number> --answer <text> [--project <path>] [--json]

codeclosure intake status <intake-run-id> [--json]
codeclosure intake audit <intake-run-id> [--json]
```

`intake submit` and `intake clarify` invoke one Runtime-owned Intake operation
and return its stored or current typed result. The CLI MUST NOT expose a raw
`materialize` command that can consume a stale derived
`READY_TO_MATERIALIZE` view. The deterministic `MATERIALIZE` Decision and Goal
authority commit together.

`intake clarify` accepts no caller-restated question data beyond the supplied
Question ID; Runtime resolves its retained `questionSpecDigest`, exact
`questionDigest`, issuing Decision binding, and answer schema and binds them
into command input. Runtime accepts it only when that question belongs to the
Intake Run, is the single current unanswered question, remains bound to current
authority, and its answer schema accepts the supplied input. M2.5 emits exactly
one active question per `CLARIFY`; it supports neither positional nor batch
answers.

An accepted clarification atomically creates a new Raw Request revision whose
semantic digest embeds the exact Question/Decision tuple, one unique immutable
`ClarificationAnswerBinding` that additionally binds the revision and command,
and a cleared singular `activeQuestionRef`. The Question is never mutated and
historical bindings are queried separately from current IntakeRun state.

`intake clarify --project` is permitted only as structured user input when that
exact question allows project identity to be established or corrected. Trusted
composition normalizes the path and adds it to the isolation lease before Store
activation; retained project roots remain in that lease. After activation,
Runtime validates the exact Intake ID, expected version, principal, question
ID, both question digests, issuing Decision, canonical command digest, and
normalized path before committing a new Raw Request revision; that command
digest includes the normalized path when present. Free-form `--answer` text and
assistant output cannot introduce project-path authority, and status/audit
commands accept no project override. A stale, foreign, already answered,
mismatched, or unrelated question produces no Raw Request revision, lifecycle
mutation, or assistant invocation; the
deterministic admitted-rejection transaction still records the exact
reservation, `REJECTED` outcome, observed version, and audit.

Direct `goal create` remains unchanged. It MUST NOT synthesize Raw Request,
Proposal, Projection, Admission, Materialization, or Start-Authorization
history.

### 5.3 Pre-Goal command identity and idempotency

Existing `processed_commands` authority is Goal/Workflow-bound and MUST NOT be
made to target a fabricated Goal before Materialization. Under
[ADR 0034](../adr/0034-close-pre-goal-command-replay-and-sqlite-activation.md),
M2.5 adds a distinct Intake command contract with two immutable record kinds:

```text
IntakeCommandReservation
  -> one exact canonical command input has claimed an Intake operation

IntakeCommandOutcome
  -> one exact APPLIED | REJECTED | FAILED final result for that reservation
```

Every reservation binds `CommandId`, closed operation kind, trusted principal,
target RawRequest/IntakeRun, canonical input digest, expected and observed
Intake version, operation identity, and causal time. For external work it also
binds the exact Intake/Answer-only Manifest ID/digest, installed Admission
Policy, adapter, and response-contract identities. It commits with the initial
Raw Request/IntakeRun authority, exact operation Manifest/bindings, and audit
before an assistant call. A separate Store-authored immutable outcome binds the
exact final Intake records, audit, status, safe result projection, and
disposition afterward.

A clarification reservation additionally binds the exact
`ClarificationQuestionId`, retained `questionSpecDigest`, exact
`questionDigest`, issuing Decision ID/digest, and answer schema. The caller
supplies only the Question ID and cannot restate those retained bindings. M2.5
permits exactly one current unanswered question; question order is never part
of command meaning.

The reservation transaction also persists the new Raw Request revision with
its embedded `AnsweredQuestionBinding`, a unique immutable
`ClarificationAnswerBinding`, the cleared `activeQuestionRef`, updated
IntakeRun version/status, exact Manifest/external-operation bindings, and audit
before any fresh analysis call.

A deterministic admitted rejection commits its reservation, `REJECTED`
outcome, observed Intake version, and audit together without a Raw Request
revision, Intake lifecycle mutation, or external call. Invalid input, missing
target, replay-integrity failure, and command conflict are not stored as
admitted rejections.

`APPLIED` includes `CLARIFY`, intentional `NO_EXECUTION`, successful
Materialization, and `NO_EXECUTION / ANSWER_FAILED`. `REJECTED` stores only a
deterministic admitted command rejection. `FAILED` requires one successfully
committed terminal Intake Failure Record; Store, audit, codec, clock,
replay-integrity, command-conflict, or unrecorded adapter failures do not become
stored `FAILED` outcomes.

Exact duplicate delivery MUST NOT call the assistant twice:

- replay of a final entry returns the stored Intake result without new Intake,
  Admission, Goal, Workflow, Materialization, Start-Authorization, or Intake
  audit authority;
- an active matching reservation returns a typed non-authoritative
  `IN_PROGRESS` view or joins the same in-process operation without creating
  another effect;
- the same `CommandId` with another input digest conflicts;
- a concurrent loser cannot create a second Raw Request revision, Proposal,
  Decision, Goal, or Start Authorization; and
- a retained orphan reservation is reconciled during startup before any new
  assistant call.

The Intake contract is not a Workflow command journal, Worker receipt,
Acceptance Decision, or completion authority. The separately preallocated
ordinary `StartGoal` still uses `processed_commands`; an Intake outcome cannot
replace it. Any implementation that diverges from ADR 0034 or weakens ADRs 0009
through 0013 MUST stop for another ADR.

After replay of a materialized `AUTHORIZE_START` result, the coordinator may
separately resubmit only that exact Start command. The ordinary command boundary
alone decides whether the missing first Start applies, an existing result
replays, or the command is rejected.

### 5.4 Persistence and migration profile

M2.5 adds one or more additive migrations beginning after current migration
`0025`. The migrations MUST introduce complete authority rather than placeholder
tables. They MUST implement ADR 0034's separate immutable reservation/outcome
records and include:

- Raw Request roots and immutable revisions;
- IntakeRun current state and optimistic version;
- Intake command reservations/outcomes;
- Intake Manifests and operation bindings;
- Proposals and Projection revisions;
- Source Bindings, Material Ambiguities, Clarification Questions, and
  Clarification Answer Bindings;
- installed Admission Policies and installation audits;
- closed Admission Decision variants;
- Answer-only Responses and Intake Failure Records;
- Goal Materialization Records and optional Goal Start Authorizations; and
- Intake-owned audit/query relationships.

The Store MUST enforce immutable rows, parent chains, exact digest bindings,
terminal-reference unions, action/outcome/disposition combinations, uniqueness
of one Materialization per admitted Projection, and at most one exact Start
Authorization for `AUTHORIZE_START`. For `CLARIFY`, it MUST independently
recompute the question-spec, Decision, and exact Question-record digests;
validate every repeated spec field and Decision/Question cross-reference; and
commit the Decision, Question, single active reference, Intake transition,
audits, and command outcome atomically.

For an accepted clarification, the Store MUST also recompute the new Raw
Request and Answer Binding digests; validate their exact Question, Decision,
parent revision, Intake, Command, and current-reference relationships; permit
only one Answer Binding per Question; clear the singular active reference; and
persist that whole answer boundary atomically. Missing, duplicate, cross-Intake,
or digest-mismatched Answer Bindings, an active already-answered Question, and
any `NEEDS_CLARIFICATION`/`ANALYZING`/terminal active-reference shape mismatch
fail strict reopen.

Migration preflight MUST reject retained placeholder, malformed, partial,
cross-run, mixed-terminal, duplicate-materialization, or unprovable Intake
authority without partial schema application. Store writes MUST immediately
read through the owning codecs, and close/reopen MUST reconstruct the exact
authority chain. SQLite constraints are defense in depth and do not become a
second Admission, Goal, or Workflow owner.

Verified SQLite activation MUST include every retained Intake project/scope
reference and every explicit invocation root under ADR 0034, including a
structured project correction supplied to `intake clarify`. Retained roots are
never replaced by caller input. Those bootstrap paths are denial inputs only;
they do not become Raw Request, Source Binding, Admission, Goal, or recovery
authority. Runtime may bind the correction only after activation and exact
question ID, question-spec/record digests, issuing Decision, and version
validation.

### 5.5 Canonical identity and causal time

Slice 1 MUST add named schema-versioned ADR 0006 projections and golden vectors
for every Intake digest. At minimum this includes Raw Request revision, Intake
Manifest, Proposal, Projection, Source Binding, Material Ambiguity set,
Clarification Question specification and record, Clarification Answer Binding,
Admission Policy, Admission Decision, Answer-only Response, Failure Record,
Materialization Record, Start Authorization, and Intake command input/result.

Record IDs, Runtime-authored observation timestamps, and each digest field are
excluded only where the owning contract declares them envelope metadata.
Semantic arrays use fixed canonical ordering. Exact admitted text is hashed as
UTF-8 bytes and the Raw Request revision separately binds the whole semantic
record. A text digest cannot substitute for a revision digest.

The acyclic `CLARIFY` projections are computed in order: first the
`ClarificationQuestionSpec.questionSpecDigest`; then the Admission Decision,
whose semantic digest includes that spec digest but excludes generated IDs;
then `ClarificationQuestion.questionDigest`, whose exact relationship
projection includes its Question ID, issuing Decision ID/digest, repeated spec,
and spec digest. The Decision MUST NOT include `questionDigest`. Golden vectors
and Store poisoning tests cover every substitution edge.

For a clarification answer, the Raw Request semantic projection first includes
the exact embedded `AnsweredQuestionBinding`. The later
`answerBindingDigest` includes that Raw Request revision/digest plus the exact
Raw Request ID, Question, Decision, Command ID, and canonical command-input
digest; it excludes the generated Answer Binding ID, Runtime-authored answer
time, and itself. The Raw Request projection MUST NOT include the later Answer
Binding identity or digest. Raw Request, Question, Decision, and Command IDs
inside these projections are governed relationship identities; only the
generated Answer Binding record ID is envelope metadata.

Runtime time obeys the current causal-floor contract. Proposal observation,
Clarification Answer Binding, Decision, Failure, Materialization, Start
Authorization, audit, and command times cannot predate their source authority.
In particular, `answeredAt` cannot predate its Question, reservation, or Raw
Request revision. Time-sensitive Admission receives an explicit source-bound
observation; it does not read ambient wall time while claiming deterministic
replay.

### 5.6 Intake Assistant and Thread policy

The baseline selects the narrowest recoverable policy:

1. each Intent-analysis or Answer-only operation starts one controlled App
   Server process, one fresh physical Thread, and one bounded Turn;
2. M2.5 never resumes or reuses a previous Intake Thread;
3. a clarification answer creates a Question-bound Raw Request revision, a
   unique immutable Answer Binding, and a new operation whose fresh Thread
   receives the complete current Intake Package and Intake Manifest;
4. Answer-only uses a distinct `AnswerOnlyPackage` and response schema and
   never receives project tools;
5. all Web Search, MCP, apps, plugins, hooks, skills, subagents, dynamic tools,
   shell/file tools, Candidate writes, and ambient project instructions are
   disabled for the Intake assistant profile;
6. the process cwd and writable state root are CodeClosure-owned, operation-
   scoped locations outside the project, Candidate, authority database, and
   credential roots;
7. unexpected Compact, Thread replacement/loss, process exit, interruption,
   malformed stream, unsupported server request, missing terminal response, or
   response-schema mismatch fails that operation; and
8. process and Thread release is attempted at every terminal boundary, but
   neither retained conversation state nor successful cleanup becomes Intake
   authority.

There is no automatic replacement Thread or assistant retry. A successfully
recordable Intent-analysis failure closes the IntakeRun as `FAILED` with a
closed reason. A process crash before that compound commit leaves `ANALYZING`
authority for operation-kind-aware startup reconciliation: Intent analysis
closes as `FAILED / INTERRUPTED_ANALYSIS`, while Answer-only closes as
`APPLIED / NO_EXECUTION / ANSWER_FAILED / INTERRUPTED_ANSWER_DELIVERY` without
another assistant call. A user-requested retry starts a new IntakeRun.

This fresh-operation policy is an M2.5 implementation choice, not a product
claim that later milestones can never retain a Thread. A future reuse policy
must still recompile the current Intake Package and cannot make conversation
history authoritative.

### 5.7 Intake packages and response contracts

The Runtime compiler creates immutable operation input from exact persisted
authority. `IntakePackage` contains only the current Raw Request chain,
optional current Projection, clarification state, declared project/scope,
Intake/Admission Policy and adapter identities, response-contract identity,
response schema, and hard budgets. `AnswerOnlyPackage` contains only the exact
Raw Request binding, prepared `NO_EXECUTION / ANSWER_ONLY` Decision binding,
exact Admission Policy ID/version/digest, adapter ID/version,
response-contract digest, and output budgets.

The durable Intake Manifest records every included or intentionally omitted
input, its revision, provenance, digest, and budget decision. Neither package
may contain fabricated Goal, Workflow, Attempt, Worker Session, Candidate,
Evidence, Acceptance, Workflow Policy binding, or Execution Profile binding.

The assistant returns only closed untrusted values:

- Intent analysis returns one bounded `IntentAnalysisProposal`; and
- Answer-only returns bounded content or a typed adapter failure observation.

The Coordinator, not the adapter, allocates record identity, classifies safe
failure, validates source spans, constructs Source Bindings and ambiguities,
computes digests, and persists authority. Unknown fields, raw exceptions,
private reasoning, transcript content, tool attempts, model-authored IDs, and
oversized output never enter authoritative records or audit.

### 5.8 Optional project observation is deferred

The basic M2.5 implementation does not add the optional project-exploration
port. The Intake assistant receives no project tool capability and cannot
produce `PROJECT_OBSERVED` authority in the baseline.

A request that requires governed repository inspection MUST NOT be classified
as Answer-only merely because it is read-only. When its source-bound formal
intent is otherwise admissible, M2.5 materializes a formal read-only Goal whose
later `DISCOVERY` phase owns the inspection. Project-assisted Intake remains an
M3 candidate under the existing exact-root, read-only capability, budget,
provenance, omission, and revalidation requirements.

### 5.9 Deterministic Admission Policy

Trusted composition installs one immutable bounded local Admission Policy from
a definition without a caller-authored digest. Runtime computes its canonical
identity; Store independently recomputes it and commits the policy plus
installation audit atomically.

The policy MUST define:

- required formal Goal fields and at least one explicit required Criterion;
- permitted source classes for each material field;
- meaning-preserving derivation rules;
- ambiguity classification and bounded question ordering;
- exactly one active question per M2.5 `CLARIFY` result;
- action/outcome/execution-disposition combinations;
- `ANSWER_ONLY`, `POLICY_DENIED`, `UNSUPPORTED`, and `ABANDONED` aggregation;
- exact Workflow Policy/Profile preflight for `AUTHORIZE_START`; and
- a stable ordered reason trace.

Fixed canonical input and policy produce the same outcome, reason trace, and
Decision digest. The Admission Engine has no assistant-call, Goal-write,
Workflow-write, Store-write, Worker, Candidate, Acceptance, or external-effect
capability.

For `GOVERNED_EXECUTION`, trusted composition selects the exact installed
Workflow Policy and Execution Profile. The CLI and assistant do not select or
override them. Missing or incompatible configured Start authority produces a
typed Intake preparation failure; it MUST NOT silently downgrade to
`MATERIALIZE_ONLY` or create a Goal without the promised governed-execution
causality.

### 5.10 Answer-only, failure, and recovery

A deterministic preflight MAY produce `PRE_ANALYSIS_NO_EXECUTION` without an
Intent-analysis call. For `ANSWER_ONLY`, a separate bounded assistant operation
then returns `ANSWER_RETURNED` or a safe `ANSWER_FAILED` reason. The final
compound transaction stores the Decision, Answer-only Response, terminal
`NO_EXECUTION`, audit, and command result together.

When deterministic preflight is dispositive and no Answer-only or other
external operation is required, one transaction stores any admitted Raw
Request revision, current Intake authority, command reservation, closed
`NO_EXECUTION` Decision, terminal status, `APPLIED` command outcome, and audits.
It does not create an intermediate `ANALYZING` operation or split the already-
known result across transactions.

Answer delivery failure remains `NO_EXECUTION / ANSWER_FAILED`; it is not an
Intake processing failure. Answer content is a non-authoritative result and
cannot become a Source Binding, Fact, Criterion, Human Decision, Goal,
Workflow, Evidence, Acceptance, or execution instruction.

An analysis, preparation, or future observation failure that can be recorded
stores one terminal Failure Record, `FAILED` status, audit, and command result
atomically. Store/audit failure cannot be reported as a successfully recorded
failure. Startup recovery runs before publishing Intake handlers and dispatches
only structurally valid non-resumable orphaned `ANALYZING` operations by their
immutable reservation operation kind. Non-Answer-only analysis orphans become
one audited `FAILED / INTERRUPTED_ANALYSIS` result. An Answer-only orphan
deterministically revalidates the exact retained prepared Admission input and
commits one `APPLIED / NO_EXECUTION / ANSWER_FAILED /
INTERRUPTED_ANSWER_DELIVERY` result without recalling the assistant. Missing or
irreproducible inputs, operation/state mismatch, and corrupt or contradictory
authority fail strict reopen.

### 5.11 Materialization and separate Start

For a current deterministic `MATERIALIZE` result, one Store transaction MUST
independently revalidate and atomically persist:

- the exact Admission Decision;
- formal Goal revision 1 validated by Goal Manager;
- one initial `DISCOVERY / READY` Workflow constructed by Workflow Runtime;
- the synchronized initial Goal lifecycle projection;
- one immutable Goal Materialization Record;
- exactly one Goal Start Authorization for `AUTHORIZE_START`, otherwise none;
- all Intake, Goal, Workflow, Admission, Materialization, and optional
  Start-Authorization audits; and
- the final Intake command outcome.

Materialization creates no Attempt, Context, Policy/Profile Workflow binding,
dispatch claim, Worker process, Candidate, Evidence, or Acceptance. After the
transaction commits, the application coordinator may submit only the
preallocated ordinary `StartGoal` command carried by the Start Authorization.
That existing command retains freshness, first Policy/Profile binding, Context,
Attempt, dispatch, idempotency, and recovery authority.

The public composite result keeps three independent dispositions:

- Answer: `NOT_REQUESTED`, `ANSWER_RETURNED`, or `ANSWER_FAILED`;
- Materialization: no Goal, materialized ready, or materialization failure; and
- Start: `NOT_AUTHORIZED`, `READY_PENDING_START`,
  `START_COMMAND_APPLIED`, `START_COMMAND_REJECTED`, or
  `START_INFRASTRUCTURE_FAILURE`.

A crash between transactions leaves a visible recoverable `READY` Goal. Replay
of the Intake outcome creates no new Intake or Materialization authority; the
coordinator may then separately resubmit only the exact preallocated Start
command. If first Start never committed, that ordinary command may perform it.
If it did commit, processed-command replay cannot recreate its bindings or
redispatch its retained Attempt. A different explicit manual `StartGoal` races
through ordinary first-Start guards and produces at most one winner. Start
failure never rolls back or misreports successful Materialization.

### 5.12 Read views, privacy, and retention

Runtime owns schema-versioned Intake status and audit views. They expose the
exact current revision/provenance chain, unresolved ambiguity, single active
question ID, specification/record digests, issuing Decision binding, and answer
schema; historical Question-to-Answer-Binding relationships; Decision reason,
Answer disposition, terminal Failure/next action, materialized Goal reference,
and separate Start disposition. They cannot issue Admission, materialize,
retry, Start, or declare technical completion.

The first local retention profile MUST be named, versioned, bounded, and
deterministic. It MUST:

- admit exact valid UTF-8 user content only within fixed byte limits;
- reject prohibited or unsupported content rather than insert synthetic
  replacement text into authoritative bytes;
- retain exact safe source bytes while dependent Admission or Materialization
  authority remains usable;
- keep redacted display and safe audit projections separate;
- exclude raw adapter exceptions, credentials, private reasoning, unknown
  response fields, and unrestricted transcripts from authority and audit; and
- mark unavailable content explicitly so it cannot satisfy a new
  `USER_STATED` binding.

M4 may add richer privacy and erasure UX. M2.5 MUST NOT claim that a digest
alone preserves source authority after the exact permitted bytes are gone.

### 5.13 Proof layering

The mandatory M2.5 verdict is deterministic. It uses a controlled App Server
fixture through the real lower client and Intake Adapter, real SQLite
transactions/reopen, and the real existing Goal/Workflow/Start boundaries.
Model output is fixed untrusted input for repeatable authority proof.

A separate bounded live Intake Adapter observation MAY exercise the supported
installed Codex App Server. Its semantic Proposal or answer is not prescribed,
cannot replace deterministic proof, cannot self-materialize, and is not
required for the unconditional M2.5 verdict unless the milestone boundary is
explicitly amended before execution.

## 6. Transaction map

| Operation | External work | Required atomic commit | Failure meaning |
| --- | --- | --- | --- |
| New Intake analysis reservation | none | RawRequest, revision 1, IntakeRun `ANALYZING`, command reservation, exact Manifest/external-operation bindings, audit | no assistant call before commit |
| New Answer-only reservation | none | RawRequest, revision 1, IntakeRun `ANALYZING`, command reservation, exact Answer-only Manifest/prepared Admission input/adapter/response-contract bindings, audit | no Answer-only assistant call before commit |
| Clarification reservation | none | exact current Question/Decision binding, new Raw Request revision with embedded answered-question tuple, unique immutable Answer Binding, cleared singular active reference, IntakeRun version/status, command reservation, exact Manifest/external-operation bindings, audit | stale, foreign, answered, duplicate/cross-Intake Answer Binding, Decision/spec/record mismatch, or positional input creates no new analysis |
| Deterministic command rejection | none | reservation, `REJECTED` outcome, observed Intake version, audit | no Raw Request revision, lifecycle mutation, or external call |
| Immediate deterministic no-external terminal | none | current Intake authority, any admitted Raw Request revision, reservation, closed `NO_EXECUTION` Decision, terminal status, `APPLIED` outcome, audits | no intermediate `ANALYZING`, assistant call, or split known result |
| Intent analysis | one fresh process/Thread/Turn outside Store transaction | Proposal, Manifest binding, Projection, Source Bindings, ambiguities, next Decision/status and, for `CLARIFY`, its exactly bound Question; audit and final command result | safe failure becomes terminal `FAILED`; Store failure is not recorded success |
| Answer-only | one fresh process/Thread/Turn outside Store transaction | `NO_EXECUTION` Decision, Answer-only Response, terminal status, audit, final command result | delivery failure is `ANSWER_FAILED`, not Intake `FAILED` |
| Materialization | assistant work already complete | Decision, Goal, Workflow, Materialization, optional Start Authorization, audits, final command result | no partial formal authority |
| Automatic Start | ordinary `StartGoal` effect after Materialization commit | existing first-Start transaction and processed outcome | Goal remains materialized `READY` if Start does not apply |
| Startup reconciliation | no assistant call | operation-kind-aware result: non-Answer-only analysis orphan commits Failure, `FAILED`, audit, and `FAILED` outcome; Answer-only orphan commits deterministic `NO_EXECUTION`, bounded `ANSWER_FAILED / INTERRUPTED_ANSWER_DELIVERY`, audit, and `APPLIED` outcome | missing or irreproducible input, operation/state mismatch, or corrupt authority blocks reopen |

## 7. Slice sequence

### Slice 0 — final interface and decision closure

Deliverables:

- capture the exact M2 public facade, Store, App Server client, Policy, Profile,
  CLI, migration, and dependency baseline;
- fix the built-in Admission Policy identity, assistant profile, response
  contracts, byte/count/time budgets, local principal, retention profile, and
  governed-execution Workflow Policy/Profile selection;
- adopt ADR 0034's immutable Intake command reservation/outcome contract and
  verified-activation extension without reinterpretation;
- fix the exact rejection-versus-ignore behavior for model-authored authority
  fields and authority language inside otherwise allowed proposal content;
- confirm the remaining compound transaction shapes;
- add dependency-gate expectations for the new adapter; and
- record any further durable conflict as an ADR before authority code.

Proof:

- no product code claims Intake behavior;
- every planned type has one owner and one prohibited-capability list; and
- no unresolved decision can change authority, persistence, retry, or public
  action meaning in a later slice.

### Slice 1 — domain, codecs, policy, and invariant

Deliverables:

- add typed Intake identifiers and closed record unions to `packages/domain`;
- add semantic invariants, canonical projections, runtime decoders, and golden
  digest vectors, including the acyclic Question-to-Raw-Request-to-Answer-
  Binding chain;
- add the deterministic Admission Policy definition, installer inputs, and
  Engine contracts; and
- add the canonical Runtime invariant equivalent to “Intent proposals cannot
  admit or materialize themselves” together with executable invariant metadata
  and adversarial tests in the same change.

Proof:

- every unknown field, invalid scalar, enum, terminal shape, and digest drift
  fails decoding;
- Question records remain immutable, and Answer Binding uniqueness/current-
  reference invariants reject an answered active Question;
- fixed Admission input produces one semantic Decision digest; and
- no Proposal/Projection value can construct Goal or Workflow authority.

### Slice 2 — SQLite Intake authority

Deliverables:

- add complete migrations after `0025`;
- implement policy installation, command reservation/outcome, analysis,
  clarification, non-execution, failure, Materialization, and query Store ports;
- implement compound Goal/Workflow/Materialization/Start-Authorization writes;
- add startup validation, immediate-read, close/reopen, and migration preflight;
  and
- implement ADR 0034's verified SQLite activation extension so retained Intake
  project references participate in data-home/project isolation checks without
  becoming Goal authority.

Proof:

- failure injection after every new write leaves no partial authority;

  Bindings, fails Store reopen;
- exact command replay and concurrent clarification/materialization losers create
  one respective effect; and

### Slice 3 — packages, manifests, and Intake Assistant Adapter

Deliverables:

  Evidence, or Acceptance capability;

### Slice 4 — Coordinator, Projection, clarification, and Admission

Deliverables:

  isolation before Runtime binding;
- validate Proposal, construct Projection revisions, Source Bindings, Material
  Ambiguities, one bounded question specification, and the acyclic
  Decision-to-Question record chain;
- construct the Question-bound Raw Request revision and unique immutable Answer
  Binding without mutating the Question;
- implement deterministic preflight and Admission over exact snapshots;
- atomically commit `CLARIFY` and non-Answer `NO_EXECUTION`; and
- expose typed in-process status views for active and non-execution runs.

Proof:

- model-proposed-only material fields cannot materialize;
- `READY_TO_MATERIALIZE` is never durable authority;

  unique Answer Binding, clears the active reference, and preserves immutable

  unrelated question input cannot create a revision or external call; embedded
  answered-question or Answer-Binding substitution fails closed; prompt,

### Slice 5 — Answer-only, terminal failure, and restart

Deliverables:

Proof:

- `ANSWER_FAILED` remains distinct from Intake `FAILED`;
- a failed IntakeRun cannot reopen or call the model again; and
- orphan reconciliation creates exactly one operation-appropriate
  `INTERRUPTED_ANALYSIS` or `INTERRUPTED_ANSWER_DELIVERY` result without a model

- a crash before Start leaves one visible `READY` Goal;

## 8. Independent exit assessment

The exit assessment is not an implementation Slice. It begins only after
Slices 0 through 7 have completed their implementation deliverables and the
entry conditions in the
[M2.5 acceptance plan](m2.5-acceptance-plan.md) are satisfied.

The assessment sequence is:

1. execute the canonical `accept:m2.5` procedure on one exact declared source
   identity;
2. inspect its complete executable matrix, actual diff, working-tree state,
   isolation/effect trace, and evidence manifest;
3. create the independent dated M2.5 completion review under the acceptance
   plan's narrow review-file source-identity rule;
4. rerun the required documentation and offline closure checks on the
   review-bearing tree; and
5. let the independent review issue the only bounded milestone verdict.

## 11. Milestone completion rule

The independent review may issue the bounded M2.5 `PASS` only after:

1. Slices 0 through 7 are implemented with their focused evidence;
2. the canonical `accept:m2.5` procedure runs on one exact source identity;
3. every mandatory row passes with no waiver, expected failure, or hidden
   assistant retry;
4. every M1 and M2 regression gate remains green;
5. strict SQLite reopen proves the complete Intake-to-Goal chain;
6. documentation describes implemented and planned behavior consistently;
7. the review-bearing tree passes the required offline and source-closure
   checks; and
8. the independent review finds no blocker, unavailable mandatory evidence, or
   conditional waiver.

No implementation Slice, acceptance runner, fixture, assistant response, or
stored Goal result may issue that milestone verdict.

That verdict proves only the bounded M2.5 Goal Intake and Materialization
vertical slice. It does not prove project-assisted Intake, complete
requirements understanding, Goal revision, rich conversation routing, product
completion, production readiness, or external-effect authority.
