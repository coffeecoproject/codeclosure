# M2.6 Unified Frontstage Interaction and Control implementation plan

- Status: Draft; formal decisions are proposed and implementation has not
  started
- Plan date: 2026-08-06
- Milestone: M2.6
- Milestone boundary: [CodeClosure milestones](../milestones.md#m26--unified-frontstage-interaction-and-control)
- Domain contract: [Frontstage Interaction](../frontstage-interaction.md)
- Milestone assessment: [M2.6 acceptance plan](m2.6-acceptance-plan.md)

## 1. Purpose and completion meaning

This plan converts the proposed M2.6 frontstage contract into bounded,
reviewable implementation slices. The goal is one continuously available local
CLI frontstage where the user provides natural-language input only while
CodeClosure retains trusted routing, an exact Pending Action for every member
of the closed new-Intake/Goal-control action set, deterministic
direct-or-separate confirmation, Goal Intake, Goal query/control, Workflow, and
Acceptance authority.

Creating or completing this plan does not implement M2.6. Completing every
slice would establish an implementation candidate only. M2.6 becomes complete
only after the canonical zero-skip assessment and an independent dated review
issue an unconditional bounded verdict.

Nothing in this plan authorizes merge, release, deployment, communication,
purchase, production mutation, or another external effect.

## 3. Entry conditions

Implementation MUST NOT start until:

1. the [M2.5 completion review](../reviews/m2.5-completion-review.md) remains an
   unconditional `PASS` for its recorded source identity and bounded claim;
2. every mandatory deterministic and live row in the [M2.5.1 acceptance
   plan](m2.5.1-acceptance-plan.md) has passed on one exact source identity and
   an independent review has issued an unconditional bounded `PASS`;
3. that M2.5.1 review proves real Answer-only, real Intent analysis, real
   clarification, Materialization, exact real M2 Profile binding, ordinary
   Start, isolated-Candidate mutation, protected verification, and regression
   closure without revising the historical M2.5 claim;
4. ADR 0036 through ADR 0039 have accepted dispositions;
5. this plan and the independent acceptance plan are linked from repository
   indexes and the milestone boundary;
6. the complete M1/M2/M2.5/M2.5.1 regression baseline is green on the
   implementation base revision;
7. the installed Interaction Routing Policy, Frontstage Assistant Profile,
   response contracts, retention profile, and budgets are fixed for the
   bounded proof;
8. the branch/base identity and pre-existing working-tree changes are recorded;
9. no deferred item in the temporary
   [M2.6 TODO](m2.6-deferred-boundary-todo.md) is being treated as implicit
   scope; and
10. there is no unresolved higher-authority conflict.

Planning, read-only investigation, and deterministic capability probes may
occur before these conditions. They are not product implementation.

## 4. Fixed scope

The bounded implementation includes:

- durable `InteractionSession`, `InteractionMessage`,
  `InteractionOperation`, `FocusBinding`, `RouteProposal`, `RouteDecision`,
  `PendingAction`, `PendingActionResolution`, `InteractionActionReservation`,
  `InteractionActionOutcome`, `InteractionMessageHandoff`, and
  `FrontstageAnswer` records;
- closed codecs, canonical projections/digests, policies, causal time, audit,
  exact replay, strict reopen, and corrupt-state rejection;
- deterministic route admission, direct-action parser, Interaction Confirmation
  Policy, Pending Action Authorization, and closed natural-language
  confirmation parser;
- one-message exact handoff to existing M2.5 submit/clarify facades;
- a separate Frontstage Assistant port, package/manifest compiler, isolated
  fresh-operation adapter, and one bounded proposal-response union;
- a public authority-home-bound, exact-project-scoped paginated Goal-summary
  query for the fixed local principal;
- exact Focus Binding, natural-language Goal list/status/audit, and authorized
  start/resume/cancel composition through existing public Runtime facades;
- one persistent foreground CLI loop;
- one serialized Frontstage operation and at most one session-owned
  execution-bearing task, limited to governed Intake, Start, or Resume
  composition that may drive one Goal;
- bounded Runtime-owned result notifications;
- graceful shutdown plus strict startup reconciliation; and
- deterministic, failure-injection, cross-process, strict-reopen, and bounded
  live proof.

## 5. Explicit non-scope

M2.6 does not implement:

- a detached Runtime Host, daemon, or execution guarantee after CLI exit;
- project-wide Goal slots, automatic multi-Goal scheduling, or parallel Goal
  workers;
- rich TUI, web UI, graphical client, or menu workflow;
- multi-user, team, remote-runner, or cloud operation;
- full Fact Graph, broad project discovery, or project-aware ordinary chat;
- arbitrary multi-message synthesis into M2.5 user provenance;
- persistent assistant Thread reuse or Compact policy;
- automatic repair/retry or execution-time Goal revision;
- changes to technical Acceptance or closeout authority; or
- promotion, merge, release, deployment, or other external effects.

Those items are staged, without authority, in the temporary
[deferred-boundary TODO](m2.6-deferred-boundary-todo.md).
The proposed [M2.7 plan](m2.7-local-runtime-host-single-goal-control.md)
separately owns the candidate Runtime Host, control lease/observer, and project
single-active-Goal slot. It does not enlarge any M2.6 slice.

## 6. Slice sequence

### Slice 0 — Decision and proof-contract closure

Deliverables:

- accept, replace, or reject ADR 0036 through ADR 0039;
- close record fields, enums, canonical projections, policy/profile identities,
  direct-action/confirmation rules, content/retention budgets, failure families,
  and migration numbering;
- close the immutable Pending Action/Resolution/Action Reservation/Outcome
  chain and same-Command-ID crash reconciliation;
- close same-session busy behavior for another governed Intake, Start, Resume,
  Cancel, and explicit `MATERIALIZE_ONLY` Intake alternative;
- close trusted-parser ordering and the one-call Frontstage Proposal union;
- bind the fixed local principal to one authority home and exact project query
  scope without adding per-Goal principal authority;
- freeze the M2.6 acceptance matrix, proof fixtures, source-identity rule, and
  independent-review boundary;
- confirm App Server profile feasibility without claiming an empty built-in
  tool inventory; and
- remove or assign every unresolved core question from the temporary TODO.

Exit evidence:

- no implementation decision remains hidden in prose or fixture code;
- accepted decisions agree with M2.5 handoff, public Runtime, Workflow, and
  Acceptance boundaries; and
- all probes are labelled non-implementation evidence.

### Slice 1 — Interaction Domain and policy

Deliverables:

- branded identifiers and closed records for the fixed scope, including
  immutable Pending Action Resolution and Action Reservation/Outcome records;
- owning codecs for every external, Runtime, Store, and reopen boundary;
- canonical projections and digest profiles with golden vectors;
- deterministic Interaction Routing Policy, direct-action parser, Interaction
  Confirmation Policy, authorization-disposition, and separate-confirmation
  parser contracts;
- illegal-state matrices for session, operation, focus, route, handoff, and
  pending action; and
- invariants preventing assistant self-routing/self-authorization.

Required proof:

- malformed, partial, unknown-field, oversized, cross-session, stale, and
  digest-substituted shapes fail closed;
- the same policy input yields the same semantic Route Decision; and
- only one exact current Pending Action may obtain one Resolution and, when
  authorized, one Action Reservation/Outcome chain.

### Slice 2 — SQLite interaction authority

Deliverables:

- append-only migrations and schema fingerprint updates;
- atomic session/message/operation/pending-action/resolution/action-reservation/
  focus/outcome transactions;
- Store-authored outcome envelopes and typed replay/conflict results;
- immediate-read and close/reopen validation; and
- startup detection of incomplete Frontstage operations.

Required proof:

- injected failure at every compound-write boundary leaves no partial
  authority;
- strict reopen rejects missing audit, invalid relationship, digest mismatch,
  illegal lifecycle, reused pending action, and unclosed operation shapes; and
- concurrent consumers produce one winner and a typed loser.

### Slice 3 — Frontstage packages and Assistant Adapter

Deliverables:

- `FrontstageContextPackage` and durable Manifest compiler;
- one closed `FrontstageProposalResponse` union for answer, route,
  clarification, and no-action proposals;
- protocol-neutral `FrontstageAssistantPort`;
- deterministic fake App Server and bounded real compatibility fixture;
- fresh isolated Thread/Turn adapter under the accepted effect profile; and
- closed mapping for protocol, process, timeout, lifecycle, output, retention,
  and observed-tool failures.

Required proof:

- only the closed source set reaches the package;
- every selected/omitted source, profile, policy, response contract, and budget
  is digest-bound;
- dependency checks prove the adapter has no control or project capability;
- observed tool use discards all output; and
- exact replay performs no second assistant call.

### Slice 4 — Routing, confirmation, and M2.5 handoff

Deliverables:

- Runtime coordinator for route reservation, assistant invocation, deterministic
  decision, pending-action creation, and result commit;
- trusted confirmation, focused-question, direct-action, and read-query parsers
  before at most one Assistant proposal operation;
- deterministic direct-user authorization plus closed separate
  confirmation/decline/unclear handling;
- immutable authorization Resolution plus public-action Reservation/Outcome
  composition with one preallocated Command ID;
- exact one-message submit and clarification handoffs to public M2.5 facades;
- bounded ordinary Frontstage answers outside Intake; and
- redacted session/audit projections.

Required proof:

- no model output can issue a trusted interaction action;
- answer/read routes receive no mutation capability;
- every member of the closed new-Intake/Goal-control action set cannot execute
  without an exact Pending Action and allowed authorization disposition;
- direct authorization is restricted to exact low-risk action kinds and cannot
  use model interpretation as evidence;
- cancellation, replacement, destructive, conflicting, or ambiguous actions
  require a separate response or clarification;
- an active session-owned execution-bearing task blocks another governed Intake,
  Start, or Resume without creating delayed authority, while an exact
  `MATERIALIZE_ONLY` Intake alternative requires separate authorization;
- handoff preserves exact user bytes and does not include summaries or Runtime
  delimiters; and
- Intake replay, Materialization, Start, clarification, and failure semantics
  remain unchanged.

### Slice 5 — Goal discovery, focus, and control

Deliverables:

- authority-home-bound, exact-project-filtered, stable, paginated
  `listGoalSummaries` public query for the fixed local principal;
- startup active-Goal summary and natural-language list/status/audit views;
- exact Goal and Intake Focus Binding coordination;
- direct-or-separately-authorized public Start/Resume/Cancel composition; and
- bounded result/progress notifications derived from Runtime authority.

Required proof:

- direct and Intake-created Goals appear together without cross-project leak;
- ambiguous or stale references cannot choose a mutation target;
- a refreshed view invalidates a stale pending action;
- command replay/races preserve one Runtime-owned outcome; and
- no view or notification can issue Acceptance or closeout.

### Slice 6 — Persistent CLI and bounded concurrency

Deliverables:

- foreground read/evaluate/render loop for natural-language messages;
- serialized Frontstage operations and one session-owned execution-bearing task;
- non-blocking bounded notification delivery;
- signal/EOF shutdown ordering without implicit Goal cancel; and
- trusted composition that publishes the loop only after Store activation and
  recovery.

Required proof:

- the frontstage remains responsive while one execution-bearing task runs;
- the session does not automatically launch a second execution-bearing task;
- a busy-session governed request is neither silently downgraded nor retained
  for delayed Start, and only an explicitly confirmed `MATERIALIZE_ONLY` Intake
  alternative may proceed;
- local concurrency is not misrepresented as a project-wide scheduler; and
- existing public Runtime/Store rules decide cross-process races.

### Slice 7 — Recovery, failure, and cross-process closure

Deliverables:

- operation-kind-aware startup reconciliation;
- exact same-Command-ID reconciliation for unresolved authorized public actions;
- strict reopen of session/focus/pending action/operation/handoff/result state;
- graceful and abrupt shutdown fixtures;
- notification-loss and rendering-failure recovery; and
- real separate-process CLI continuation against one authority home.

Required proof:

- orphaned assistant work becomes one typed terminal result without model
  recall;
- unresolved authorized public work re-enters only the same idempotent Command
  ID and produces no replacement command or duplicate authority effect;
- an interrupted Goal uses existing Runtime recovery and no consumed dispatch
  is redispatched;
- CLI exit creates no `CancelGoal` absent exact confirmation; and
- the next status query reproduces authority even if a notice was lost.

### Slice 8 — Canonical assessment and independent review

Deliverables:

- one fail-closed non-verdict `accept:m2.6` runner;
- exact source manifest and sole review-file exclusion;
- zero-skip execution of every mandatory acceptance row;
- complete M1/M2/M2.5/M2.5.1 regression execution on the assessed source; and
- an independent dated completion review with one unconditional or failed
  bounded verdict.

The runner cannot issue the milestone verdict. A review is not `PASS` when any
row is failed, skipped, waived, expected to fail, or not applicable without
predeclared justification in the acceptance contract.

## 7. Required walking demonstration

The final deterministic demonstration must show:

1. trusted startup opens one principal/project session and the frontstage stays
   available;
2. an ordinary question returns one bounded Frontstage Answer and creates no
   Goal or Intake authority;
3. “列出目标” returns a paginated Runtime-owned view containing both direct and
   Intake-created fixtures;
4. an ambiguous Goal reference asks for clarification rather than selecting a
   target;
5. a clear low-risk natural-language governed-work request produces one exact
   Pending Action and deterministic `DIRECT_USER_AUTHORIZED` disposition;
6. that action is consumed once and hands the exact originating message bytes
   to M2.5 without requiring a redundant confirmation turn;
7. an exact Intake clarification continues through the existing Question
   binding and materializes one Goal;
8. Start remains the separate ordinary M2.5 boundary, uses M2.5's preallocated
   `GoalStartAuthorization`, and resolves the exact real M2 Codex Execution
   Profile proven by M2.5.1 when governed execution was admitted;
9. while that Goal runs, the user can ask for status through the same
   frontstage; and
10. CLI shutdown/reopen reconciles session and Goal state without implicit
    cancel, duplicate command, assistant recall, or dispatch replay.

Supplementary branches must cover a cancellation or ambiguous mutation that
requires and consumes one separate natural-language confirmation, plus
declined/expired confirmation, forbidden direct authorization, assistant
failure, observed tool use, stale focus, command race, Answer-only separation,
notification loss, busy-session governed-work/`MATERIALIZE_ONLY` handling,
action-call crashes before and after the public command commit, abrupt process
exit, and a correct first-pass Goal path without fabricated failure.
