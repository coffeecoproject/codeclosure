## 1. Purpose and completion meaning

This plan closes one established pre-B5 capability gap: the pinned Codex
`0.146.1` App Server `readOnly` sandbox prevents the selected snapshot write
but does not confine reads to the exact candidate-free project-read snapshot.
The real probe successfully opened a content-free Authority Home sentinel and
failed with
`DENIED_BOUNDARY_READ_SUCCEEDED_AUTHORITY_HOME`.

The required outcome is an enforceable, version-bound execution boundary in
which:

- candidate-free `DISCOVERY` and `PLAN` may read only their exact owned
  selected-source snapshot;
- those phases cannot write that snapshot and cannot read the source checkout,
  repository control data, Authority Home, credentials, Candidate roots,
  protected assets, sibling snapshots, or other forbidden roots;
- `IMPLEMENT` may read and write only through its exact Candidate lease and
  remains subject to Candidate Manager-owned freeze-v2 allowed-path proof; and
- App Server model/authentication transport remains usable without making
  credentials or control authority readable to model-usable commands.

Completing this plan does not complete Slice 4 or M2.5.1. It only permits B5 to
restart when the same exact supported execution boundary passes deterministic
and explicitly authorized real black-box proof.

## 2. Established facts

The following facts are inputs to this plan and MUST NOT be weakened into
warnings or optional rows:

1. The frozen new-operation baseline remains Codex CLI `0.146.1` with protocol
   snapshot
   `sha256:312156edfdf765f134ce5f754419a9509fd34186798a1bdbb0c219ac7c19c610`.
2. Its generated `SandboxPolicy` union contains `dangerFullAccess`,
   `readOnly { networkAccess }`, `externalSandbox { networkAccess }`, and
   `workspaceWrite { writableRoots, networkAccess, ... }`. It contains no
   explicit candidate-free read allowlist or read-denial member.
3. The B4 probe now invokes the pinned App Server `command/exec` sandbox path
   directly. It does not ask a model to reproduce the command and does not
   infer denial from model prose or inactivity.
4. The candidate-free command could read its selected snapshot member, could
   not write that snapshot, and could read the content-free Authority Home
   sentinel. The last observation establishes that `readOnly` is not the ADR
   0043 read perimeter.
5. The diagnostic retained no protected file content, user request text,
   assistant content, reasoning, credential content, raw protocol payload, or
   unrestricted command output. The CodeClosure and demonstration source
   repositories remained unchanged, and owned assessment roots were cleaned.
6. Earlier diagnostic Intake and composition success cannot replace the failed
   containment row and cannot become final Slice 4 evidence after later source
   changes.
7. This failure does not revoke the historical M1, M2, or M2.5 verdicts and
   does not reinterpret Slice 3's deterministic protocol-fixture proof as
   Live evidence.

The current public Codex documentation may be used to discover candidate
capabilities, but only the candidate installation's generated schema,
versioned configuration projection, and real black-box behavior can establish
support. Documentation for a newer release MUST NOT be projected backward onto
the frozen `0.146.1` protocol.

## 3. Root cause, owning layer, and preserved contracts

The failed requirement is effective Worker filesystem isolation. Its owning
chain is:

```text
trusted composition
  -> installed external-backend capability and Execution Profile
  -> phase isolation and permission identity
  -> Codex App Server Adapter/client mapping
  -> effective host/App Server sandbox enforcement
  -> independent black-box containment observation
```

The root cause is not Intent Admission, Workflow transition, Candidate
allowed-path comparison, Evidence, or Acceptance. The current external backend
capability and phase Profile claim a read boundary that the selected App Server
sandbox cannot enforce. Therefore:

- Runtime invariants I-023 and I-030 remain unchanged: phase permissions must
  be enforced outside prompts, and claims may not exceed proof strength;
- ADR 0028 remains the owner of version-bound external capability,
  configuration, credentials separation, and black-box enforcement;
- ADR 0043 remains the owner of the exact candidate-free snapshot and forbidden
  read boundary;
- ADR 0044 remains the owner of Candidate base-to-frozen changed-path proof and
  does not repair candidate-free read exposure; and
- the B4 Receipt remains assessment evidence only and cannot become Domain,
  Runtime, Store, Audit, Evidence, Acceptance, or closeout authority.

The Intake Adapter, Admission Engine, Workflow state machine, Candidate timing,
protected verification, and Acceptance Engine require no redesign merely
because the current backend sandbox is insufficient.

## 4. Scope and non-scope

This sub-plan includes:

- an exact read-only capability comparison between `0.146.1` and deliberately
  selected candidate Codex releases;
- metadata-only black-box probes over exact candidate-free and Candidate-bound
  root matrices;
- one explicit accepted-ADR decision between a supported version transition and
  a separately isolated external execution boundary;
- the smallest additive Profile, capability, Adapter/client, trusted
  composition, test, and documentation changes required by the selected route;
  and
- restart of the existing B5 sequence only after effective containment passes.

It does not add:

- M2.6 Frontstage, M2.7 Host, scheduling, multiple Goals, detached execution,
  retry, replan, repair expansion, Goal revision, promotion, release, or
  deployment;
- user-, model-, project-, or CLI-selected execution profiles;
- a source-checkout read grant for candidate-free Codex;
- a Candidate before `PLAN -> IMPLEMENT`;
- a production FakeWorker fallback;
- model self-report, prompt instruction, file mode, path hiding, post-run source
  equality, or `commandActions` classification as containment proof; or
- a broad sandbox framework or provider abstraction for hypothetical workers.

## 5. Serial work sequence

The batches are serial because implementation identity cannot be frozen until
the capability investigation reaches one closed conclusion and an accepted ADR
selects one enforceable route.

### C0 — Freeze the blocker and preserve diagnostic meaning

Before another Live command:

- keep B5 blocked and keep the failed reason code exact;
- retain `0.146.1` Profile and protocol identities with their existing meaning;
- do not rewrite the B4 test to accept the exposed read;
- do not treat the successful selected-file read or denied snapshot write as a
  substitute for forbidden-root denial; and
- confirm that the containment command continues to emit only metadata and
  content-free exit classification.

C0 changes documentation and deterministic diagnostic coverage only. It adds
no supported backend identity.

### C1 — Candidate Codex capability spike

Run a read-only, separately authorized capability spike outside product
authority. Before installing a candidate, freeze one closed comparison set in
the non-verdict diagnostic record
`docs/reviews/m2.5.1-slice4-read-containment-capability-investigation.md`.
The set MUST contain `0.146.1` and at most two published stable successors,
each selected because its official release material or generated contract
indicates a concrete filesystem-containment change relevant to the failed read
boundary. It MUST NOT scan releases version by version or keep adding
candidates after seeing probe results.

For every frozen comparison member, capture:

- exact Codex binary version, delegated executable identity, and content
  digest;
- generated App Server protocol snapshot and canonical digest;
- generated sandbox, Thread, Turn, and `command/exec` request/response types;
- exact configuration and permission-profile projections;
- any explicit readable-root allowlist, read-denial set, external-sandbox, or
  equivalent enforcement surface; and
- whether the surface is available to both real Worker Turns and the direct
  black-box command probe without a generic arbitrary-method escape.

The spike MUST regenerate or inspect the candidate's actual protocol. It MUST
NOT hand-copy a type from current documentation, modify production Profile
identities, migrate retained authority, or install a candidate as the product
default.

A candidate is eligible for black-box proof only when its complete generated
contract can represent all of these properties without prompt reliance:

1. exact candidate-free readable snapshot root;
2. no candidate-free writable project root;
3. exact forbidden source, authority, credential, Candidate, protected, and
   sibling roots;
4. exact Candidate-bound writable root for `IMPLEMENT`;
5. command network disabled and approval policy `never`;
6. no danger-full-access or silent sandbox fallback; and
7. App Server authentication without exposing its credential source to the
   command sandbox.

### C2 — Candidate black-box matrix

For each eligible candidate, run the existing content-free probe shape in an
isolated temporary installation and state root. The exact matrix is:

| Phase | Path class | Required observation |
| --- | --- | --- |
| `DISCOVERY` / `PLAN` | selected snapshot regular file | read succeeds |
| `DISCOVERY` / `PLAN` | selected snapshot write | denied |
| `DISCOVERY` / `PLAN` | source checkout and repository control data | read and write denied |
| `DISCOVERY` / `PLAN` | Authority Home and credential root | read and write denied |
| `DISCOVERY` / `PLAN` | Candidate, protected-asset, sibling-snapshot, and unrelated operation roots | read and write denied |
| `IMPLEMENT` | exact Candidate lease | required read and bounded write succeed |
| `IMPLEMENT` | source, Authority Home, credentials, protected assets, sibling snapshots, and other Candidate roots | read and write denied |

Every probe MUST additionally prove exact effective isolation identity, command
request identity, no approval, no project-command network, zero retained
command output, unchanged opening/closing source identity, and complete owned
process/root cleanup. A missing attempt, unsupported request, model refusal,
generic process failure, or absent sentinel is not access denial.

### C3 — Capability conclusion gate

The investigation has one closed capability conclusion:

- `SUPPORTED_CODEX_READ_CONTAINMENT_PROVEN` — at least one exact candidate
  release represents and passes the complete matrix; or
- `NO_REVIEWED_CODEX_READ_CONTAINMENT_PROVEN` — no reviewed release can
  establish the required read boundary, or authentication and command
  isolation cannot be separated safely.

`UNKNOWN`, partial success, candidate-free-only success, documentation-only
support, or an unexplained warning blocks the conclusion. The investigation
record is non-authoritative engineering evidence: it MUST NOT select an
implementation route, install production authority, or unblock B5. A new
accepted ADR must use that capability conclusion to bind the durable selected
route before production behavior changes.

## 6. Route A — Versioned Codex capability

When C3 proves `SUPPORTED_CODEX_READ_CONTAINMENT_PROVEN` and a new accepted ADR
selects Route A, the smallest coherent implementation is an additive version
transition. The current lower Client has one bundled installation/protocol
identity shared by Intake and Worker invocation, while retained Goal execution
bindings close over exact Profile ID, version, and digest. Route A therefore
MUST close those existing consumers rather than replace the bundle in place.

1. accept an ADR that records the exact new binary/protocol baseline, effective
   read-containment capability, retained compatibility, black-box proof, and
   whether the transition is Worker-only or covers the entire new-operation
   Intake-plus-Worker toolchain;
2. keep the Runtime-owned installed Execution Profile binding plus its exact
   `ExternalBackendCapabilityRecord` as the only production version selector;
   no CLI, user, Adapter, diagnostic, or ambient installation may choose a
   version independently;
3. add a new immutable external-backend capability and a new formal Execution
   Profile ID/version/digest tuple for new M2.5.1 operations rather than
   overwriting the retained Profile selected by existing Goal bindings;
4. retain the `0.146.1` Profile, Adapter, generated protocol, Intake, and
   external-execution records without rehash, reinterpretation, automatic
   resume, or substitution;
5. if Intake remains on `0.146.1`, add an internal exact versioned
   installation/protocol selection below the existing lower-client boundary so
   Intake keeps the retained bundle while Worker uses the accepted successor;
   if the entire new-operation toolchain moves, add a new Intake Profile and
   Adapter identity instead of silently running retained Intake v3 on the new
   protocol;
6. update the existing closed M2.5.1 Profile-family classification, governed
   preflight support, formal Profile installer/reopen, Runtime Profile registry,
   trusted production activation, and Worker invocation so the new exact tuple
   is supported and cannot be misclassified as historical authority;
7. version every canonical projection or Adapter/client contract whose semantic
   field set changes; if the existing v3 phase entry can reconstruct and bind
   the exact new read policy, prove that sufficiency explicitly rather than
   widening it informally;
8. update trusted composition and the Adapter to resolve only the exact
   capability bound by the new Profile for the formal live path, with no
   fallback to `0.146.1`, a Fake component, danger-full-access, or ambient
   latest installation;
9. preserve ordinary Start binding and strict existing-Goal reopen without a
   second version registry or caller-selected migration; and
10. add strict install, reopen, replay, retained-old/new coexistence, cross-
    version substitution, missing-capability, and failed-containment tests
    before another B5 attempt.

Changing only a version string or permission-profile digest is insufficient
when the effective readable-root contract changes. Conversely, an additive
Domain or Store schema MUST NOT be introduced when the changed policy remains
fully reconstructible from an existing versioned Profile projection and its
new immutable identity.

## 7. Route B — External containment boundary

When C3 concludes `NO_REVIEWED_CODEX_READ_CONTAINMENT_PROVEN`, implementation
remains stopped until a new accepted ADR selects Route B. The design must
establish a real separation between:

- a trusted host/control side that owns authentication, configuration,
  Authority Home access, Profile validation, and App Server lifecycle; and
- a phase-restricted command/effect side that can see only the exact
  candidate-free snapshot or Candidate lease granted for that operation.

Merely running the App Server and its credential file in the same container,
using `externalSandbox` without an already enforced outer sandbox, changing
file modes, or wrapping commands in a cooperative script does not establish
that separation. The ADR must define:

- process and operating-system-principal topology;
- how model-usable commands cross the restricted execution boundary;
- exact per-phase readable, writable, network, approval, and integration sets;
- credential injection that is usable by the trusted transport but absent from
  the command namespace;
- process ownership, interruption, timeout, crash, and cleanup behavior;
- versioned capability/Profile/Adapter identities and strict reopen behavior;
- metadata-only observations returned to the existing Adapter/Runtime chain;
  and
- deterministic plus real black-box proof at the same strength as C2.

The external boundary MUST reuse the existing narrow Runtime external-
execution and Worker Adapter abstractions when they still represent their
owners. It may add the smallest required execution port or process split only
when otherwise the implementation would duplicate policy, expose credentials,
or make the Adapter a second authority. A Codex fork may be considered only
after the accepted ADR records why the supported App Server plus host isolation
cannot meet the contract.

## 8. Required implementation and validation gates

Whichever route is selected, completion requires all of the following on one
exact source identity:

- generated protocol and canonical snapshot checks;
- capability/Profile installation, strict decode, migration when applicable,
  reopen, replay, and substitution coverage;
- focused lower-client and Adapter tests;
- trusted-composition dependency and no-fallback checks;
- deterministic B3 linked-chain and B4 containment suites;
- the complete C2 real black-box matrix for the selected formal Profile;
- unchanged source project and CodeClosure source identity;
- no retained sensitive content or owned temporary resources; and
- `corepack pnpm check:m2.5.1:slice0`, relevant focused suites,
  `corepack pnpm docs:check`, and `corepack pnpm gate:quality` passing with no
  failed, skipped, todo, waived, expected-fail, or unexplained-warning result.

A passing containment Receipt remains assessment evidence. It does not replace
the Candidate Manager-owned freeze-v2 record, protected verification,
Evidence, Acceptance, or closeout authority.

## 9. B5 restart sequence

B5 may restart only after the selected formal Profile passes the gates above.
It then restarts from the beginning rather than combining old diagnostics with
new source:

1. freeze one clean exact CodeClosure source identity and demonstration
   baseline;
2. run the initial real Intake, real linked composition, and real containment
   validation as diagnostics on that same identity;
3. update implemented-but-not-milestone-assessed documentation and prepare the
   excluded Slice 4 review draft;
4. run all focused deterministic owners and the complete quality gate;
5. capture the four outer source identities required by the parent B5 plan;
6. run the final real Intake, linked composition, and containment commands in
   order without an intervening source change;
7. cross-bind exact toolchain, Profile, project, Candidate, freeze-v2, and
   containment Receipt identities; and
8. edit only the excluded Slice 4 review file and issue only the bounded
   decision whether Slice 5 may begin.

No earlier successful Intake, composition, lower-client, or M2 Worker receipt
may substitute for a final command after the selected containment implementation
changes.
