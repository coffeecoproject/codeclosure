## 1. Purpose and completion meaning

This plan closes one established pre-B5 capability gap: the pinned Codex
`0.146.1` App Server `readOnly` sandbox prevents the selected snapshot write
but does not confine reads to the exact candidate-free project-read snapshot.
The real probe successfully opened a content-free Authority Home sentinel and
failed with
`DENIED_BOUNDARY_READ_SUCCEEDED_AUTHORITY_HOME`.

The required outcome is an enforceable, version-bound execution boundary in
which:

- candidate-free `DISCOVERY` and `PLAN` may read only their exact owned
  selected-source snapshot;
- those phases cannot write that snapshot and cannot read the source checkout,
  repository control data, Authority Home, credentials, Candidate roots,
  protected assets, sibling snapshots, or other forbidden roots;
- `IMPLEMENT` may read and write only through its exact Candidate lease and
  remains subject to Candidate Manager-owned freeze-v2 allowed-path proof; and
- App Server model/authentication transport remains usable without making
  credentials or control authority readable to model-usable commands.

Completing this plan does not complete Slice 4 or M2.5.1. It only permits B5 to
restart when the same exact supported execution boundary passes deterministic
and explicitly authorized real black-box proof.

## 3. Root cause, owning layer, and preserved contracts

The failed requirement is effective Worker filesystem isolation. Its owning
chain is:

```text
trusted composition
  -> installed external-backend capability and Execution Profile
  -> phase isolation and permission identity
  -> Codex App Server Adapter/client mapping
  -> effective host/App Server sandbox enforcement
  -> independent black-box containment observation
```

The root cause is not Intent Admission, Workflow transition, Candidate
allowed-path comparison, Evidence, Acceptance, or a missing Codex capability.
The production preparation assigns one writable permission profile to every
phase, while the Adapter and direct probe replace that configured profile with
generic request-level sandboxes. The selected App Server can enforce the
required boundary when the exact phase profile remains effective. Therefore:

- Runtime invariants I-023 and I-030 remain unchanged: phase permissions must
  be enforced outside prompts, and claims may not exceed proof strength;
- ADR 0028 remains the owner of version-bound external capability,
  configuration, credentials separation, and black-box enforcement;
- ADR 0043 remains the owner of the exact candidate-free snapshot and forbidden
  read boundary;
- ADR 0044 remains the owner of Candidate base-to-frozen changed-path proof and
  does not repair candidate-free read exposure; and
- the B4 Receipt remains assessment evidence only and cannot become Domain,
  Runtime, Store, Audit, Evidence, Acceptance, or closeout authority.

The Intake Adapter, Admission Engine, Workflow state machine, Candidate timing,
protected verification, and Acceptance Engine require no redesign. The direct
correction belongs to formal Profile construction, controlled launch, the
lower Client, Worker Adapter mapping, and their effective-isolation proof.

## 4. Scope and non-scope

This sub-plan includes:

- an exact read-only capability comparison between `0.146.1` and deliberately
  selected candidate Codex releases;
- metadata-only black-box probes over exact candidate-free and Candidate-bound
  root matrices;
- an explicit determination whether an existing accepted architecture suffices
  or a new ADR-level route is required;
- the smallest additive Profile, capability, Adapter/client, trusted
  composition, test, and documentation changes required by the selected route;
  and
- restart of the existing B5 sequence only after effective containment passes.

It does not add:

- M2.6 Frontstage, M2.7 Host, scheduling, multiple Goals, detached execution,
  retry, replan, repair expansion, Goal revision, promotion, release, or
  deployment;
- user-, model-, project-, or CLI-selected execution profiles;
- a source-checkout read grant for candidate-free Codex;
- a Candidate before `PLAN -> IMPLEMENT`;
- a production FakeWorker fallback;
- model self-report, prompt instruction, file mode, path hiding, post-run source
  equality, or `commandActions` classification as containment proof; or
- a broad sandbox framework or provider abstraction for hypothetical workers.

### C2 — Candidate black-box matrix (completed)

For each eligible candidate, run the existing content-free probe shape in an
isolated temporary installation and state root. The exact matrix is:

| Phase | Path class | Required observation |
| --- | --- | --- |
| `DISCOVERY` / `PLAN` | selected snapshot regular file | read succeeds |
| `DISCOVERY` / `PLAN` | selected snapshot write | denied |
| `DISCOVERY` / `PLAN` | source checkout and repository control data | read and write denied |
| `DISCOVERY` / `PLAN` | Authority Home and credential root | read and write denied |

Every probe MUST additionally prove exact effective isolation identity, command
request identity, no approval, no project-command network, zero retained

generic process failure, or absent sentinel is not access denial.

The retained `0.146.1` baseline passed the complete empty-sentinel matrix with
separate configured read-only ProjectRead and writable Candidate profiles.
The probe directly denied the actual temporary App Server `CODEX_HOME`, source
and simulated `.git`, Authority, protected, Candidate escape, sibling, and
unrelated roots; it allowed only the selected snapshot read or Candidate
read/write required by the phase. A Thread created without a sandbox override
reported the same inherited profile class and disabled network. The isolated
`0.147.0` comparison also passed the direct matrix, but adds no required
capability and is not selected.

This capability spike made no model call or Turn and is not formal production
Worker evidence. It proves that the locked backend can enforce the boundary
that production composition must now select and re-prove.

### C3 — Capability conclusion gate (closed)

## 6. Selected correction — retained `0.146.1` phase profiles

The smallest coherent solution retains the exact `0.146.1` binary and protocol
snapshot and corrects the composition of existing authorities. It MUST NOT
reinterpret the already reviewed Profile v1 tuple or silently change an
existing Goal binding. New operations therefore receive one additive formal
Profile version and exact digest while the retained version remains strictly
reopenable with its historical meaning.

The implementation sequence is:

1. keep the existing Runtime Profile registry as the sole selector and add one
   supported M2.5.1 Profile version for new operations; do not add a caller,
   CLI, Adapter, or ambient-version selector;
2. retain the exact Codex version, delegated binary, protocol snapshot, Intake
   Profile, and lower generated protocol; no toolchain migration is involved;
3. materialize one ProjectRead permission profile with workspace `read` and one
   Candidate permission profile with workspace `write`, both with root default
   deny, minimal toolchain read, local-control denial, temporary-root denial,
   disabled network, and approval `never`;
4. bind each existing Profile v3 phase entry to the correct exact permission
   profile ID/digest and effective configuration digest; `DISCOVERY` and `PLAN`
   may share the one semantically identical ProjectRead profile, while
   `IMPLEMENT` selects the Candidate profile;
5. extend controlled App Server launch with one narrow validated permission-
   profile selector that emits only the exact `default_permissions` startup
   override; it MUST NOT accept arbitrary configuration text or a generic
   argument list;
6. add one bounded lower-client command operation that inherits the selected
   configured profile by omitting request-level `sandboxPolicy`, while retaining
   the existing fixed method, absolute cwd, argv, timeout, output cap, decoder,
   process ownership, and shutdown boundaries;
7. update only the new v3 Adapter mapping selected by the additive Profile so
   Thread and Turn inherit the launch-selected profile; retained Adapter paths
   keep their existing request semantics;
8. update effective Thread/config/profile checks, the B4 probe, and trusted
   invocation to bind the same exact phase selection without prompt inference
   or a second policy owner;
9. preserve ordinary Start, Candidate timing, freeze-v2, protected
   verification, Evidence, Acceptance, closeout, failure closure, and no-Fake-
   fallback behavior unchanged; and
10. add strict install, reopen, replay, retained-v1/new-v2 coexistence,
    substitution, missing selection, explicit sandbox override, forbidden-root,
    process cleanup, and output-privacy coverage before another B5 attempt.

No Domain, Store, Workflow, Candidate, Evidence, or Acceptance schema change
is required. The existing phase entry already owns the necessary protocol-
